# Research: How the RW Lock Works (Implementation Review)

**Date**: 2026-05-12 19:23:33 ACST
**Researcher**: Harry Nguyen
**Git Commit**: b114c9474b8e165caf8a8fa078bcc9271db3a676
**Branch**: feature/RW-replica
**Repository**: sql-fs

## Research Question

Investigate how the hand-rolled readers-writer lock (`RWLock`) actually works in the codebase, cross-referencing the architecture described in `DEVELOPER.md` and the design doc `thoughts/shared/research/2026-05-10_13-03-37_parallel-readonly-bash-exec.md`. Verify the live implementation matches what the docs claim, identify the exact state machine, the writer-priority + batch-wake mechanics, the AbortSignal contract, and how the lock is composed with `readOnlyContext` (AsyncLocalStorage), `SqlFs.beginReadOnlyScope`, and the `withSessionRead` entry path.

## Summary

The implementation in `src/api/rw-lock.ts` matches what `DEVELOPER.md` and the research doc describe. It is a small (~190 LOC) async readers-writer lock with three live state fields (`#readers`, `#writerActive`, `#queue`) and two public entry methods (`runShared`, `runExclusive`). Writer-priority is enforced by `#hasQueuedWriter()` blocking new readers from the fast path; the batch-wake invariant is implemented in `#dispatch()` by draining all consecutive shared waiters in a single pass; `AbortSignal` rejects queued waiters cleanly without affecting already-held locks.

The lock composes with three other mechanisms to make parallel readers safe against a shared `SqlFs`:

1. **`session.lock.runShared`** (in `SessionManager.withSessionReadEntry`, session-manager.ts:533-620) bounds the reader cohort.
2. **`SqlFs.beginReadOnlyScope()` / `endReadOnlyScope()`** (sql-fs.ts:569-589) flips a refcounted depth counter; every mutating method calls `#assertWritable` (sql-fs.ts:591-597) before any DB work and throws `EREADONLY`.
3. **`readOnlyContext` AsyncLocalStorage** (read-only-context.ts:15-19) gives each `withSessionRead` call its own `{ violated: boolean }`, so `#assertWritable` can attribute a violation to the offending reader's async stack without poisoning innocent concurrent readers.

The read path additionally **skips `publishVersionIfDirty`** and **skips `scriptTx`** entirely (the latter via `readOnlyContext.getStore() !== undefined` in `execWithRuntimeThrottle`, session-manager.ts:1093-1138). `ensureFreshCache` is single-flighted across the cohort via `session.freshCacheInflight` (session-manager.ts:622-659).

Routes (`/exec-sync`, `/exec` SSE, `/exec-sync-batch`, MCP `bash_exec` / `bash_exec_batch`) branch on `body.readOnly` to select between `withOwnedSessionOrRehydrate` (write) and `withOwnedSessionRead` (read), and map `EREADONLY_VIOLATION` to HTTP 422.

## Detailed Findings

### 1. RWLock state machine (`src/api/rw-lock.ts`)

State fields (rw-lock.ts:35-38):

```typescript
#readers = 0;
#writerActive = false;
readonly #queue: Waiter[] = [];
```

A `Waiter` (rw-lock.ts:22-29) is `{ mode: "shared" | "exclusive", resolve, reject, signal?, onAbort?, settled }`.

#### Fast path on `#acquire` (rw-lock.ts:75-92)

- **Shared, line 78-84**: take the lock immediately iff `!#writerActive && !#hasQueuedWriter()`. This is the only line that enforces writer-priority on entry — a queued writer blocks newcomer readers even when the lock is "free of writers".
- **Exclusive, line 86-89**: take immediately iff `!#writerActive && #readers === 0`.

If neither fast-path matches, both modes fall through to `#enqueue()` (rw-lock.ts:91).

#### Writer-priority test (rw-lock.ts:178-184)

```typescript
#hasQueuedWriter(): boolean {
    for (const w of this.#queue) {
        if (w.settled) continue;
        if (w.mode === "exclusive") return true;
    }
    return false;
}
```

Linear scan — fine because queue depth is small in practice. Skips settled (aborted) waiters so aborted writers don't keep blocking readers.

#### Batch-wake in `#dispatch()` (rw-lock.ts:147-176)

Called from both `#releaseShared` (rw-lock.ts:136) and `#releaseExclusive` (rw-lock.ts:144). Algorithm:

1. **Shift settled waiters off the head** (line 148-150). Cleans up aborted entries before any decision.
2. **Bail if writer still active** (line 151). Defensive; dispatch is only called by releasers but cheap to recheck.
3. **If head is exclusive** (line 154-159): take the lock for it only if `#readers === 0` (i.e. all readers have drained); otherwise return — the in-flight readers will trigger another dispatch when they release.
4. **Otherwise head is shared** (line 165-175): loop, draining every consecutive shared waiter, incrementing `#readers`, resolving each. Stops at the first non-shared (writer) waiter, preserving writer-priority for the next round.

This is the "every consecutive shared waiter in one pass" behavior DEVELOPER.md:146 describes.

#### Abort handling (rw-lock.ts:75-76, 122-126, 115-119)

- Pre-aborted signal at acquire time: `if (signal?.aborted) return Promise.reject(makeAbortError())` — never enters the queue.
- During queuing: `signal.addEventListener("abort", onAbort, { once: true })` attaches a listener that calls `waiter.reject` → splices the waiter out of the queue and rejects with `{ name: "AbortError", code: "ABORTED" }`.
- Settled waiters are idempotent: `if (waiter.settled) return` at the top of both `resolve` and `reject` (rw-lock.ts:105-106, 113-114). This is the reason a late wake on an already-aborted waiter is a no-op.
- Once the lock is held, abort is ignored — interrupting mid-section would leave invariants broken.

#### Public API surface

| Member | Purpose |
|---|---|
| `runShared<T>(fn, signal?)` (rw-lock.ts:57) | Acquire shared, run, release; resolves to `fn`'s result. |
| `runExclusive<T>(fn, signal?)` (rw-lock.ts:66) | Acquire exclusive, run, release. |
| `get activeReaders` (rw-lock.ts:41-43) | Diagnostic. |
| `get writerHeld` (rw-lock.ts:46-48) | Diagnostic. |
| `get pendingCount` (rw-lock.ts:51-55) | Unsettled queue length (excludes aborted waiters). |

Release helpers throw if called when no holder exists (rw-lock.ts:132-143): `"RWLock: releaseShared called with no active readers"` / `"... no active writer"`. These are invariant assertions — useful in tests but should never fire because `runShared`/`runExclusive` always pair acquire with release in `finally`.

### 2. `readOnlyContext` AsyncLocalStorage (`src/api/read-only-context.ts`)

```typescript
export interface ReadOnlyContext { violated: boolean; }
export const readOnlyContext = new AsyncLocalStorage<ReadOnlyContext>();
```

A per-call context object propagated through the async stack. The single field `violated` is mutated by `SqlFs.#assertWritable` to attribute a read-only violation to the *calling* request, not to a shared FS-level flag. This is what guarantees innocent reader B is not poisoned by a lying reader A running in parallel — the doc highlights this at DEVELOPER.md:212-213 and it is implemented by `readOnlyContext.run(ctx, () => fn(session))` in `withSessionReadEntry` (session-manager.ts:553).

### 3. `SessionManager.withSessionReadEntry` (session-manager.ts:533-620)

Read path. Step-by-step:

1. **`ensureFreshCache`** (session-manager.ts:622-659) is called **before** acquiring the shared lock. It single-flights the Redis GET + `coherent.reload()` via `session.freshCacheInflight`: the first reader sets the in-flight promise, subsequent readers await the same promise, and the `.finally` clears it. This collapses N readers' version probes into one Redis round trip and at most one `reload()`.
2. **`session.lock.runShared(...)`** — multiple readers run concurrently here.
3. Inside the shared block:
   - `asReadOnlyFs(session.fs)` → duck-type for the read-only-capable FS.
   - `roFs.beginReadOnlyScope()` increments the FS-level refcount.
   - Build `ctx = { violated: false }` and run `readOnlyContext.run(ctx, () => fn(session))`. `fn` ultimately calls `execWithRuntimeThrottle` → `bash.exec`, and every `SqlFs` mutating method that runs inside this stack will see `readOnlyContext.getStore() !== undefined`.
4. **Error handling** has two arms:
   - **Raw `EREADONLY` escapes** (e.g., bash redirections like `echo x > f` synchronously reject rather than turning into a non-zero exit): catch, log audit, and rethrow as `{ code: "EREADONLY_VIOLATION" }`.
   - **`ctx.violated` set after a clean return**: the script finished but a mutating syscall was tagged earlier. Throw `EREADONLY_VIOLATION` so the route returns 422 even when the script swallowed the inner error.
5. **`finally`** — `endReadOnlyScope()` is called only when this entry actually opened it (`scopeOpened` guard) and `session.inFlight--`. Critically: `publishVersionIfDirty` is **not** called on the read path.

### 4. `SqlFs` read-only scope & `#assertWritable` (`src/fs/sql-fs/sql-fs.ts`)

Refcounted scope (sql-fs.ts:569-589):

```typescript
get readOnlyScopeActive(): boolean { return this.#readOnlyDepth > 0; }
beginReadOnlyScope(): void { this.#readOnlyDepth++; }
endReadOnlyScope(): void {
    if (this.#readOnlyDepth === 0) throw new Error("endReadOnlyScope: no active read-only scope");
    this.#readOnlyDepth--;
}
```

Assertion (sql-fs.ts:591-597):

```typescript
#assertWritable(path: string, op: string): void {
    if (this.#readOnlyDepth > 0) {
        const ctx = readOnlyContext.getStore();
        if (ctx !== undefined) ctx.violated = true;
        throw createEreadonly(path, op);
    }
}
```

Mutating methods that call `#assertWritable` at the top (verified from sql-fs.ts):

- `bulkIngest` (sql-fs.ts:651)
- `writeFile` (sql-fs.ts:689)
- `appendFile` (sql-fs.ts:741)
- `mkdir` (sql-fs.ts:809)
- `rm` (sql-fs.ts:887)
- `chmod` (sql-fs.ts:959)
- `utimes` (sql-fs.ts:973)
- `cp` (sql-fs.ts:1090)
- `mv` (sql-fs.ts:1179)
- `symlink` (sql-fs.ts:1257)
- `link` (sql-fs.ts:1293)

The check happens **before any DB call**. This is why unit tests on dialect mocks see zero spurious connections / transactions on a violation, as DEVELOPER.md:212 claims.

### 5. `execWithRuntimeThrottle` skips `scriptTx` in read mode (session-manager.ts:1093-1138)

```typescript
const inReadOnlyScope = readOnlyContext.getStore() !== undefined;
const execFn = async (): Promise<BashExecResult> => {
    if (!inReadOnlyScope && session.scriptTx !== undefined) {
        session.scriptTx.beginScope();
        try {
            const result = await session.bash.exec(script, opts);
            await session.scriptTx.endScope();
            return result;
        } catch (err) {
            await session.scriptTx.abortScope();
            throw err;
        }
    }
    return session.bash.exec(script, opts);
};
```

Two reasons documented in DEVELOPER.md:222 and confirmed by code:
- No writes can occur, so the per-script DB transaction has nothing to commit.
- The shared `SessionScopedFs` would race across concurrent readers if every reader called `beginScope`/`endScope` on the same instance.

## Architecture Insights

1. **Three independent mechanisms cooperate** to keep parallel reads safe against a *single shared* `SqlFs` instance:
   - RWLock shared mode (cohort boundary)
   - Refcounted read-only scope on `SqlFs` (FS-layer enforcement, pre-DB)
   - `readOnlyContext` AsyncLocalStorage (per-call violation attribution)
   None alone is sufficient: RWLock alone can't tell a "lying" script from a clean one; an FS boolean flag alone can't attribute the violation to one of N concurrent callers; AsyncLocalStorage alone can't stop the write from reaching the DB. Together they form a defense-in-depth chain.

2. **Writer-priority is enforced in exactly one place at acquire time** — the `#hasQueuedWriter()` check in `#acquire` (rw-lock.ts:78-81). This is the rule that prevents indefinite reader starvation. `#dispatch` then only ever wakes one *contiguous* shared run before pausing at the next writer.

3. **The read path deliberately skips Lock 2 (distributed Redis exec lock)**. This is the single-replica feature trade-off DEVELOPER.md calls out at lines 20 and 92-94. Cross-replica reader/writer coherence still works via the version counter probe in `ensureFreshCache`, but it is now a "best-effort point-in-time view" rather than a serialized one.

4. **Single-flight cache freshness is essential, not optional**: without `session.freshCacheInflight` (session-manager.ts:622-659), a wave of N parallel readers would all issue independent Redis GETs and potentially independent `coherent.reload()` calls, defeating the parallelism gains.

5. **The `scriptTx` skip on the read path is a correctness fix**, not just an optimization. Multiple concurrent readers calling `beginScope`/`endScope` on the same `SessionScopedFs` would corrupt its open-transaction state.

6. **`destroy()` and `shutdown()` use `runExclusive`** as their drain primitive — they don't need explicit "wait for inFlight==0" logic because acquiring exclusive *is* the drain (DEVELOPER.md:202 row "Sandbox destruction during active exec"). `shutdown` races this against a deadline to ensure forced exit if a writer is stuck.

## Open Questions

1. **Queue ordering on aborted writers**: `#hasQueuedWriter` skips settled writers, so an aborted writer at the head of the queue doesn't block new readers. But until `#dispatch` is next called (i.e., on a release), the settled writer sits at the head. Is there a scenario where a reader takes the fast path while a not-yet-dispatched non-settled writer is enqueued because of a race? On re-reading: no — Node is single-threaded and `#enqueue` is synchronous with the abort listener registration, so the only way a writer leaves the head is via `splice` in `reject`, which sets `settled` first. Safe.

2. **`session.lock` lifetime under rehydration**: `withSessionRead` falls back to `rehydrateAndExecRead` if the session is evicted. The new session gets a fresh `RWLock`, so concurrent readers arriving during rehydration would coalesce on `getOrCreate`'s `pending` map (DEVELOPER.md:350) and then all race for the same fresh lock. Worth a follow-up test to confirm no thundering-herd of duplicate FS construction.

3. **`exec-sync-batch` with `readOnly:true`** holds the shared lock for the entire batch duration. This is the desired behavior per the doc's open question #4, but it does mean a long batch can delay a queued writer indefinitely if more readers keep arriving — writer-priority *does* eventually grant the writer, but only after the in-flight batch finishes. Not a bug, but documenting this is worthwhile.
