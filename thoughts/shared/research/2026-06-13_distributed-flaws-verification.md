## 2. Per-flaw detail

### F1 — Poisoned publish (High)
**Confirmed:** `endScriptScope` (`sql-fs.ts:618-651`) and `abortScriptScope` (`sql-fs.ts:653-689`) both run `reload(); clearDirty()` on COMMIT/abort and **swallow** a reload failure (`639-642` and `679-687`). When the same PG outage fails both the COMMIT and the recovery reload, `#dirty` stays true and `#pathCache` stays poisoned, then `withSessionEntry` runs `publishVersionIfDirty` (`session-manager.ts:614`) which INCRs Redis (independent failure domain, healthy) and — if `REDIS_PATH_SNAPSHOT_ENABLED=true` — writes a snapshot from the poisoned cache (`session-manager.ts:817-821`).
**Corrections to original review:** (a) `session-manager.ts:743` is stale — it is now the START of `ensureFreshCache`; the unconditional publish is `614`, the publish fn is `787-833`. (b) Snapshot propagation (steps 7–8) is **not** default — `REDIS_PATH_SNAPSHOT_ENABLED` defaults FALSE (`index.ts:141`, `server.ts:51`); with snapshots off a cold replica B reloads correct committed state and is NOT poisoned, so default blast radius is "replica A poisoned + counter desync," not "poison spreads to fresh replicas." (c) Original named only `endScriptScope`; `abortScriptScope` (exec-error path, `session-manager.ts` abortScope) has identical logic and is equally exposed. (d) The "SAME PG outage" framing only holds for connection/availability outages — a serialization/deadlock/deferred-constraint COMMIT failure leaves PG reachable, reload succeeds, and existing code correctly discards the poison.
**Residual concern:** After a poisoned publish, line 832 `clearDirty()` and line 830 `lastSeenVersion==counter` **freeze the poison in** — replica A will neither re-publish (dirty cleared) nor reload (versions equal). It self-heals only via idle-eviction (`SESSION_IDLE_MS`, 600s) or another replica's write. Also the poisoned `contentCache` (set at `writeFile:789`) can serve bytes with **no backing blob row** — content poison compounding path poison; `reload()` clears contentCache on success (`558`) but the poisoned path skips it.
**Fix:** Add `#cachePoisoned` + `poisoned()` getter on `ICoherentFs`; set it in **both** swallow catches (`639-642`, `679-687`); clear it on every successful `reload()` (right after `559`) and in `ready()` (~`534`). In `publishVersionIfDirty`, check `poisoned()` FIRST (before the `wasDirty`/`publishPending` gate at `791-792`): skip INCR + snapshot, set `lastSeenVersion=-1` (forces next `ensureFreshCache` reload), `publishPending=false`, throw `ECOHERENCE`. Mirror of the existing INCR-failure machinery, suppress direction. Regression test must NOT reset `failNextCommit` so the post-COMMIT reload also throws.

### F2 — Lease loss never enforced / no fencing (High)
**Confirmed:** Run-then-check at `distributed-rw-lock.ts:421-422` (writer: `const result = await fn(); if (lost) throw new LockLostError`) and legacy `distributed-lock.ts:186-187`. The critical section (including COMMIT) runs to completion before the loss flag is inspected.
**Corrections to original review:** The cited mechanism for consequence-(b) is **wrong**: in script scope both `#withTx` and `#withBareTx` route to the same `#scriptTx`, so `getBlob` (`sql-fs.ts:806`) and `writeFileComposite` (`819`) run in ONE advisory-locked tx — the "tx1 reads / tx2 writes" interleave cannot occur, and `appendFile` is already single-transaction in the exec path (so original fix-(3) is moot). The lost-update conclusion is nonetheless **real** via a different path: `appendFile` captures its base from the **in-memory pathCache** (`existing.contentSha256` at `sql-fs.ts:805`) before any lock, and `getBlob` is **content-addressed** by hash — so a zombie writer reads its stale base even after a live writer on another replica committed a newer dirent, then overwrites with new-inode(stale-base + append), erasing the live commit. Reachability is narrow: A's Redis writer flag must expire (PX leaseMs, 60s default) **before** A opens its script-tx (advisory lock acquired lazily on first write).
**Residual concern:** When `REDIS_PATH_SNAPSHOT_ENABLED`, the zombie's `publishVersionIfDirty` writes a stale-base snapshot AND primes the Redis blob cache — propagating the lost update cluster-wide to cold-starting replicas. The committed-then-lie (consequence-a) also publishes a version bump for a write the client was told (500) had failed. H7 does not help (zombie COMMIT succeeds). Legacy single-key path has the identical defect, so disabling the RW lock during rollout does not mitigate.
**Fix (two layers):** **Layer 1** (closes consequence-a, shrinks b to heartbeat gap): wire `onLost` to an `AbortController.abort()` and plumb the signal into `bash.exec` (it already accepts `opts.signal`; compose with the existing timeout signal at `exec.ts:167-181`). On loss, bash aborts → `abortScope()` → ROLLBACK; client gets a clean retryable error. Wire to `onLost` ONLY (definitive loss/expiry), not every transient renew blip (`distributed-rw-lock.ts:320-328` already distinguishes). **Layer 2** (the only complete fix): add `version BIGINT NOT NULL DEFAULT 0` to `sandboxes`; pin the expected epoch at script-scope open; add `UPDATE sandboxes SET version=version+1 WHERE id=$s AND version=$expected` inside the advisory-locked `ctx` CTE of the composite writes — zero rows updated ⇒ abort the tx ⇒ zombie COMMIT fails in PG. Must respect `set_config('app.sandbox_id')`/RLS and be wrapped in `runTrustedDbAsync`.

### F3 — Failed publish strands replicas (Medium)
**Confirmed:** On INCR failure, `publishVersionIfDirty` sets `lastSeenVersion=-1` (`806`), `publishPending=true` (`807`), throws ECOHERENCE WITHOUT clearDirty (`808-810`). Other replicas' `getex` probes (`764`) keep succeeding against the un-bumped counter and serve the pre-write tree. Repair is hostage to a later mutating write on the **same** replica.
**Corrections to original review:** Line range `916-940` is stale (now rehydrate logic); real publish is `787-833`. The "hostage to next write" claim under-states: `publishPending` is **non-durable** (in-memory `Session` field). If the reaper idle-evicts the session (`SESSION_IDLE_MS=600s`) before that write, `getOrCreate` rebuilds with `publishPending=false` and `lastSeenVersion=initialVersion` from the un-bumped counter — the pending bump is **permanently discarded**. Severity-mitigating fact: the write IS durably committed to PG, so whenever any later write bumps the counter, laggards mismatch and reload the correct tree (including the lost write). Data converges; only the visibility window is unbounded.
**Residual concern:** The `Session.publishPending` doc-comment (`199-207`) asserts a guarantee that is FALSE once the session is reaped — fix the comment. A background-retry fix must take `session.lock.runExclusive` and re-check under the lock, or it races `ensureFreshCache` (which clears `#dirty` on the `-1` reload) and risks a double INCR (V+2, forcing spurious reloads on healthy replicas).
**Fix:** Add a `pendingPublishes` Set populated in the INCR-failure branch; an unref'd `setInterval` (near `1061`) drains it via `session.lock.runExclusive(() => publishVersionIfDirty(...))` with backoff, keyed off `session.publishPending` (NOT `wasDirty`). On reap of a `publishPending` session, attempt one best-effort publish before disconnect (FS still connected). Reject DEL-key fallback (shared failure domain). Optional: 2–3 bounded in-process INCR retries before giving up.

### F4 — `rwlockEnabled=false` rollout hazard (High)
**Confirmed:** `withExecLockShared` returns `fn()` bare when `!rwlockEnabled` (`session-manager.ts:578`). With the flag off, a same-replica reader's `ensureFreshCache`→`reload()` (on a Redis blip or cross-replica version bump, `766-771`/`774`) clears `#pathCache` and `#dirty` while a local writer holds the in-process exclusive lock mid-script — vanishing the writer's uncommitted view and suppressing its publish.
**Corrections to original review:** Fix-(b) as worded ("hoist `ensureFreshCache` inside L2") is imprecise — `ensureFreshCache` is already inside the shared-lock callback (`withSessionRead:874`→`withSessionReadEntry:877`→`ensureFreshCache:658`); the bug is that `withExecLockShared` is a **no-op** when flag-off, so there is no distributed lock to be inside of. The "legacy mutex" wording is loose: in-process exclusion is the per-session `RWLock` in exclusive mode (`session.lock.runExclusive`, `595`), not async-mutex; distributed exclusion when flag-off is the single-key SET-NX lock (`570`).
**Residual concern:** Root cause is broader than the flag — `ensureFreshCache` runs BEFORE the in-process RWLock in BOTH entry paths; normal mode is safe ONLY because the distributed shared lock refuses while a writer flag is set (`ACQUIRE_SHARED_SCRIPT`), an undocumented coupling that any future weakening re-opens. The more robust harm is the **divergent cache** (not just lost INCR): `endScriptScope` success path does NOT rebuild `#pathCache`, so cache-served `stat/readdir/readFile` return wrong results silently until the next reload. RLS/SET LOCAL unaffected (reload opens its own tx via `runTrustedDbAsync`).
**Fix:** Ship fix **(a)**: when `!rwlockEnabled`, `withExecLockShared` acquires the SAME legacy single-key lock writers use (`return withDistributedLock(this.redis, execLockKey(...), fn, this.execLockOptions)`), restoring cross-replica AND same-replica reader/writer exclusion. Update the `REDIS_RWLOCK_ENABLED` doc to say flag-off **serializes reads against writers**. As flag-independent hardening, guard `SqlFs.reload()` (~`549`): `if (this.#scriptScope) return;` so a concurrent reload can never clobber an open writer's cache in any mode.

### F5 — Redis 300s availability fuse (High)
**Confirmed:** Acquire loops conflate contention with connection failure. Default path is `distributed-rw-lock.ts` (rwlock defaults true, `server.ts:50`): `acquireExclusive` catch-as-busy `248-258`, `acquireShared` `160-178`, `waitReadersDrained` `272-278`; defaults `acquireTimeoutMs=300000`/`acquireRetryMs=50` at `101-102`. Identical behavior in the legacy file the review cited (`distributed-lock.ts`).
**Corrections to original review:** Cited `distributed-lock.ts:102-121` is the LEGACY path (flag-off only); substance confirmed in the default `distributed-rw-lock.ts`. "50ms retry" is approximate — ioredis (`redis/client.ts:32-37`) sets `maxRetriesPerRequest:3`, no `commandTimeout`, `enableOfflineQueue:true`, so during a sustained outage evals may queue/block through reconnect (backoff caps 30s) — effective behavior is a hang up to ~300s, **worse** for socket pinning, not a tight spin. The `ownership.ts:60-66` docstring ("no distributed exec lock" for readOnly) is STALE — `withSessionRead` does call `withExecLockShared`. Even pure read HTTP file ops (`files.ts:104`, `:458`) route through `withOwnedSessionOrRehydrate` (exclusive), so they hang too — wider blast radius than stated.
**Residual concern:** `waitReadersDrained` (`272-278`) is a SECOND conflation site any fix must cover. A breaker must be scoped to the ACQUIRE path ONLY — the renew/release paths (`296-337`, `191-233`) deliberately treat transient errors as non-fatal; short-circuiting them would drop a valid lease (regress H4) or skip RELEASE and leak flags/ZSET entries for a full lease (60s).
**Fix:** (1) Process-wide Redis circuit breaker (new `src/redis/circuit-breaker.ts`) wired into acquire paths only (`distributed-rw-lock.ts:247,148,261`; legacy `distributed-lock.ts:110`): distinguish thrown error from contention result; after K (~5) consecutive connection-class failures, fast-fail 503; a PING/successful eval closes it. (2) Separate short error budget (~3-5s) that only advances on thrown errors, leaving genuine contention on the full window. (3) Set `commandTimeout` (~2000ms) in `redis/client.ts` so evals reject promptly. (4) Add real Redis PING to `/readyz` (`server.ts:243`). Do NOT auto-enable degrade-to-L2+L3-only (reintroduces the write race); operator-flag only if at all. Fix the stale `ownership.ts:60-66` docstring.

### F6 — Hot CAS blob contention (Medium)
**Confirmed:** `writeFileComposite` (`postgres.ts:170-218`) runs `ON CONFLICT (sha256) DO UPDATE SET last_referenced_at=now()` (line `178`) inside the advisory-locked script-tx, holding the conflicting tuple lock until the script's COMMIT. Identical touch in `bulkIngest` (`~1001`) and standalone `upsertBlob` (`~602`).
**Corrections to original review:** "Two unrelated customers serialize" is imprecise — tenancy is one DB per `tenantId` (`tenants.ts`), so contention is between sandboxes within ONE tenant DB, not across customer DBs. Strengthening: the **empty-content blob** (sha256 of zero bytes) is the single hottest row and goes through the identical touch (`writeFile` empty write at `746-762`), so any `touch f` / `> f` early in a long script holds the universal empty-blob lock for the script's duration. Also: NO `lock_timeout`/`statement_timeout` is configured anywhere — a contender blocks indefinitely, bounded only by the holder finishing / lease / `max_lifetime` (~30 min), so "up to a minute" is the script-duration estimate, not a DB ceiling.
**Residual concern:** The per-sandbox exec lock does NOT cap cross-sandbox blob-row waits; a parked writer holds a PG connection from a `max=2` pool (`postgres.ts:58`) — fleet-wide identical scaffolding can exhaust pool slots → 503s. Any fix must preserve the GC re-adoption handshake (touch + inode-insert in one tx lets REPEATABLE-READ GC raise 40001), and must cover all three touch sites.
**Fix:** Ship the **decoupled-tx** shape (NOT conditional-WHERE alone — PG locks the conflicting tuple to end-of-tx even when the WHERE filters out the update, so the lock-free claim is false). Commit the blob upsert in its own short self-committing tx (own connection, no advisory lock — blobs is unscoped CAS) BEFORE the inode/dirent composite (run the composite without the `blob_insert` CTE). Keep the touch UNCONDITIONAL so the grace window protects the freshly-committed blob during the gap. Optionally layer conditional-WHERE on top for churn reduction only. Document the momentary-orphan dependency on the grace window.

### F7 — Destroy doesn't reach warm sessions (Medium)
**Confirmed:** `deleteVersionKey` uses `redis.del` (`session-manager.ts:1053`), re-introducing the "counter-absent==0" conflation H6's TTL design was built to avoid. Replica B's next probe reads counter-absent→0, mismatches `lastSeenVersion`, reloads a deleted sandbox → empty pathCache → bewildering errors.
**Corrections to original review:** The dominant observable is NOT a clean 404 — the failure happens inside `bash.exec` resolving cwd against an empty pathCache, surfacing as non-zero exit + garbage stderr in an HTTP **200** exec response (worse than a 404, strengthens the framing). Both the exec pre-check (`exec.ts:254-255`) and real exec (`exec.ts:282`) hit the warm-session branch, so the pre-check triggers the first reload-to-empty itself.
**Residual concern:** **Never-written variant is a separate real bug** — if B observed zero writes, `initialVersion=0`, post-destroy counter also reads 0, so `0===0`, NO reload fires, and B serves its populated cache against a deleted sandbox (ghost reads/writes). A loadAllPaths-empty guard alone does NOT cover this (no reload triggered); a `-1`/sentinel tombstone does (`0 !== -1`). Blob-GC widens the window: B's ghost reads miss once GC reclaims the orphaned blobs after grace.
**Fix (layered):** PRIMARY (Redis-independent): in `reload()`/`#loadFreshPathCache` (`sql-fs.ts:400-443,549-567`) detect zero-row loadAllPaths (CTE anchor `postgres.ts:773-775` returns 0 rows only when the sandbox/root is absent) and throw `ESANDBOXGONE` instead of installing an empty cache; `ensureFreshCache` catches it, tears down the session, throws clean ENOENT → 404. SECONDARY: tombstone instead of delete — `redis.set(versionKey, 'DESTROYED', 'EX', VERSION_KEY_TTL_SECONDS)`; teach `ensureFreshCache` (after reading raw at `764`) to recognize the sentinel BEFORE the numeric parse and run teardown. Use a distinct string (not `-1`, which is already the publish-failure marker at `806`). Audit every `Number(raw)||0` clamp site (`765`, `507`, `sql-fs.ts:405`).

### F8 — Event loop is the real clock (Partially real, Low)
**Confirmed:** Three Redis leases (writer flag, reader ZSET, heartbeats) assume timely timers; a >40s loop stall voids them. Post-hoc loss check at `distributed-rw-lock.ts:419/422`. DEVELOPER.md names the GC-pause case but nothing measures it.
**Corrections to original review:** The I2 in-lock synchronous msgpack encode trigger is gated behind `REDIS_PATH_SNAPSHOT_ENABLED` (default FALSE) — in default config the only triggers are V8 GC pauses and pathological sync bash stretches, both external/bounded/documented. The in-process `RWLock` (`rw-lock.ts`) uses NO timers — a stall just makes no progress (fail-safe), so F8 applies ONLY to the three Redis leases. The 40s figure is the floor of a phase-dependent zone (40–60s remaining at stall onset), not a threshold.
**Residual concern:** RLS unaffected (each admitted replica re-runs `set_config`). Lock 3 serializes every composite write, so a split-brain second writer cannot corrupt PG — F8 alone is not a correctness threat. When `JUST_BASH_DEFENSE_IN_DEPTH=true`, heartbeat timers are created before `bash.exec` (outside the patched window), but a long sync bash stretch is exactly when renew callbacks are starved — defense-in-depth audit will NOT capture the void.
**Fix:** PRIMARY (the actual ask): `perf_hooks.monitorEventLoopDelay` at boot + per-heartbeat gap measurement (`now - expectedFireAt`), warn at `gap > renewMs` (~20s), critical at `gap > leaseMs`. Purely observational. SECONDARY (only if snapshots ever enabled): move the sync encode out of the lock window in `publishVersionIfDirty` (`817-829`) — copy `_getPathCache()` under the lock, schedule encode+SET after release (a stale deferred write fails the embedded-version equality check and falls back to loadAllPaths). Do NOT defer the INCR.

### F9a — writeFile leaks displaced contentCache entry (Low)
**Confirmed:** `writeFile` (`sql-fs.ts:738-791`) sets the new inode's bytes (`789`, guarded `byteLength > 0`) but never evicts the OLD inode's entry; `appendFile` (`849`), `bulkIngest` (`719`, guarded), `rm` (`986`/`1008`) all evict. BIGSERIAL ids never reused → dead LRU weight.
**Corrections to original review:** Slightly broader than stated — because the `set` is guarded by `byteLength > 0`, overwriting a non-empty file with an EMPTY file orphans the old entry with no overwriting set at all.
**Residual concern:** Provably unreachable (read keys on the live inode id at `1049`), so zero staleness/RLS/GC exposure. Doubly bounded: `reload()` clears contentCache (`558`) and the dead entry is LRU-evicted first. Amplifier: a warm session looping large-file overwrites without reload can accumulate orphans up to the 50MB cap, reducing effective live-cache capacity — still self-healing.
**Fix:** Before the `set` at `789`, add `const existing = this.#pathCache.get(path);` (or reuse the `743` lookup) and `if (existing !== undefined && existing.inodeId !== inodeId) this.#contentCache.delete(existing.inodeId);`. Matches `bulkIngest`'s guard at `718`. Optional: factor the evict-displaced-then-set pattern into a shared helper.

### F9b — H6 inequality unasserted (Partially real, Low)
**Confirmed:** No boot assert enforces `SESSION_IDLE_MS < VERSION_KEY_TTL` (`VERSION_KEY_TTL_SECONDS = 7d` at `session-manager.ts:69`). An operator raising the idle window re-opens the counter-reset wrap.
**Corrections to original review:** Impact is overstated — with `!==` (`774`) the session reloads anyway on mismatch; the review's own prose concedes this. The snapshot path is doubly safe (fresh GET + strict `===` at `sql-fs.ts:404`, plus 1h-vs-7d TTL). **Unit bug in the proposed one-liner:** the constant is seconds, `SESSION_IDLE_MS` is ms — any assert must multiply by 1000.
**Residual concern:** `MCP_SESSION_IDLE_MS` (`mcp/server.ts:25`, default 30 min) is a SEPARATE env-tunable idle window not covered by a SessionManager-only assert. The collision generalizes beyond `===1` to "lastSeenVersion equals the post-reset counter," and FLUSHALL/failover/maxmemory-eviction produce the same low-value reset NOT gated by idle — so the assert is necessary-but-not-sufficient; only an epoch/fence closes the class.
**Fix:** In the SessionManager constructor after `this.idleMs = ...` (`347`), add `if (this.redis !== undefined && this.idleMs >= VERSION_KEY_TTL_SECONDS * 1000) throw ...` — prefer the margin variant `idleMs <= VERSION_KEY_TTL_SECONDS * 1000 / 2` for reaper-tick + skew headroom. Scope to `redis !== undefined` (memory deployments unaffected). Apply the same bound to `MCP_SESSION_IDLE_MS` (or a shared `assertIdleBelowVersionTtl()` at boot). Audit test fixtures that pass both a mock redis and a large idleMs. File the epoch/fence (per-creation nonce stamped on the counter) as a follow-up — it is the only thing that closes the collision/failover class.

### F9c — Reaper vs straggler probe → transient 500 (Low)
**Confirmed:** The reaper sets `session.state='closing'` synchronously (`1144`) BEFORE disconnect, but a request that grabbed the session ref before that can run `ensureFreshCache`/`reload()` against a pool being disconnected → unmapped error → default 500 instead of a clean ESESSIONCLOSING.
**Corrections to original review:** A query already on the wire is NOT aborted — `pool.end()` (no timeout, `postgres.ts:76`) resolves only after sent queries finish (driver README:1241), so the surviving vector is narrower: the reload's `db()` must be issued AFTER `pool===null` (`postgres.ts:273`, uncoded Error) or after `end()` begins rejecting NEW queries (CONNECTION_DESTROYED/ENDED, which DO carry a `code` — the "no code" generalization is wrong for that sub-case; either way unmapped → 500). The IDLE trigger is closed on `getOrCreate` paths (`lastUsed` bumped at `451`); the **overBudget** trigger is the broader/realistic one.
**Residual concern:** `state` is set synchronously at `1144` before disconnect starts — the right discriminator. Fix-(b) ("take L2 before probing") is useless: the reaper is a purely in-process timer not in the distributed lock. RLS/SET LOCAL/defense-in-depth unaffected (disconnect itself wrapped in `runTrustedDbAsync`).
**Fix:** Wrap the pre-lock `ensureFreshCache` (`593`, `658`) in try/catch: `catch (err) { if (session.state === 'closing') throw Object.assign(new Error('ESESSIONCLOSING...'), {code:'ESESSIONCLOSING'}); throw err; }` → 503 retryable. Zero concurrency change.

### F9d — No FIFO fairness in distributed acquire (Low)
**Confirmed:** Acquire is a 50ms `setTimeout` sleep loop (`distributed-lock.ts:120`; `distributed-rw-lock.ts:177,257`), not a CPU spin. Cross-replica writers can be passed over.
**Corrections to original review:** "Unboundedly" is wrong — hard-bounded by `acquireTimeoutMs` (300s) then 503; bounded-then-fail, never infinite. Writer-only (readers coexist with no mutual exclusion). `server.ts:42-49` omits `acquireRetryMs`, so 50ms is hardcoded.
**Residual concern:** L1-outside/L2-inside nesting makes unfairness strictly **cross-replica** (same-replica writers serialize fairly at the L2 FIFO queue) — reachable the moment two replicas serve one sandbox, which rehydration deliberately enables. Strongly interacts with F5 (same loop conflates busy vs Redis-down). A naive Redis LIST ticket would REGRESS crash-safety (dead holder wedges the queue) — any ticket must be TTL-reaped (mirror the reader ZSET) under the `{sandboxId}` hash tag.
**Fix:** Now: add tunable `acquireRetryMs` (`REDIS_EXEC_LOCK_ACQUIRE_RETRY_MS`, already threaded) + bounded jitter (`retryMs/2 + random()*retryMs/2`) to de-synchronize competing replicas. Later (only if multi-writer-per-sandbox is real): TTL-reaped ZSET ticket inside `acquireExclusive`, governing only Phase A admission.

### F9e — O(N) directory scans (Low)
**Confirmed:** `#childPaths`/`readdir` (`sql-fs.ts:319-330`) walk the entire pathCache per call; `estimatePathCacheBytes` re-walks after every dirty exec; mv/cp subtree relink scans the full Map at `#allPathsUnder` (`1303`, `1156`).
**Corrections to original review:** The headline O(N) cost in mv is the scan at `1303`, not the loop at `1313`. Cold-start `loadAllPaths` (`postgres.ts:750`) is itself O(N) + a round-trip, so the in-memory scan is the same order as work already paid once per session — the novel cost is **repetition** (many ls/rmdir/mv per turn), supporting Low.
**Residual concern:** A children-map fix's hardest invariant is the `reload()`/`ready()` clear+repopulate (`559`) — a sidecar not rebuilt there returns stale `readdir` after a cross-replica bump. Inode-keyed lookups (`#updateCacheByInode` `338-342`, `#resolveReadEntry` `369-371`) are NOT fixed by a path-prefix map (rare; skip).
**Fix:** (A) first, higher value: incremental `#pathCacheBytes` counter adjusted at each set/delete, reset in reload/ready; expose `getPathCacheBytes()` and call it at `498`/`627` instead of `estimatePathCacheBytes`. (B) behind a benchmark: `#childrenByParent: Map<string, Set<string>>` maintained at every mutation site (cover cp/mv subtree at `1156`/`1303` and reload explicitly). Forgetting any site desyncs readdir.

## 3. Cross-cutting

**Cluster A — the publish/commit/lease seam (F1, F2, F3).** All three live at the boundary between a committed PG transaction and the Redis version publish. They share one root assumption that breaks under stress: *the in-memory cache and the published version faithfully reflect committed PG state.* F1 breaks it via correlated PG failure (publish poison), F2 via a zombie writer that commits-then-publishes after losing its lease (publish a lost update), F3 via a publish that never lands (other replicas never told). They interact viciously: F2's zombie publish and F1's poison publish BOTH propagate cluster-wide once `REDIS_PATH_SNAPSHOT_ENABLED` is on, and F3's "heal on next write" is exactly the path F1 freezes (dirty cleared) and F2 corrupts (stale base). A correct `publishVersionIfDirty` must be the single chokepoint that refuses to publish unverified state — F1's `#cachePoisoned` and F2's epoch fence and F3's drainer all converge there.

**Cluster B — locks that other invariants silently lean on (F4, F5, F9d, and F2/F8 at the edges).** The distributed RW lock is load-bearing for far more than mutual exclusion: F4 shows the same-replica cache-coherence guarantee secretly depends on the distributed *shared* lock refusing during a write; F5 shows availability depends on the acquire loop classifying errors; F9d shows fairness depends on it; F2/F8 show correctness-under-lease-loss depends on enforcement the lock never performs. Disabling or degrading the lock (F4 flag-off, F5 outage, a future degrade-mode) cascades into all of these. The lesson: the lock is treated as a black box by callers, but its failure modes leak into cache coherence, availability, and write safety.

**Cluster C — coherence-encoding conflations (F7, F9b).** Both stem from overloading the Redis version counter's value space: F7 conflates "destroyed" with "counter absent (==0)"; F9b conflates "original low version" with "post-reset low version." Both are ultimately solved by the same primitive — a distinguishable sentinel / epoch token — which is also F2's Layer-2 fence. There is a strong case to introduce one durable per-sandbox epoch and reuse it across F2/F7/F9b.

**Cluster D — observability & local-state hygiene (F8, F9a, F9c, F9e).** Lower-severity, non-correctness: missing event-loop metrics (F8), in-memory cache hygiene (F9a, F9e), error classification (F9c). Ship opportunistically.

**Recommended fix order:**
1. **F1** (High, small, self-contained) — the `#cachePoisoned` flag is a clean mirror of existing machinery and stops phantom publishes; do it first because it hardens the same `publishVersionIfDirty` chokepoint F2/F3 also touch.
2. **F4 fix-(a)** (High, small) — one-line lock fallback + a reload guard; closes a silent data-corruption window that is active *today* during any rolling deploy with the flag off.
3. **F5** (High, medium) — circuit breaker + `commandTimeout` + `/readyz` PING; removes the 5-minute outage fuse. Do before F9d (same loop) so jitter/ticket work lands on top of the breaker.
4. **F2 Layer 1** (High, medium) — abort-signal plumbing; closes the committed-then-lie and shrinks the lost-update window. Defer **Layer 2** (epoch fence) but design it now to also serve F7/F9b.
5. **F3** (Medium) — background drainer + survive-eviction; depends on F1 landing first (both touch the publish path).
6. **F6** (Medium) — decoupled blob-tx; independent, schedule in parallel.
7. **F7** (Medium) — tombstone + sandbox-gone reload guard; pairs naturally with the F2-Layer-2 epoch token.
8. **F9b boot assert, F9a, F9c, F9e, F9d, F8** (Low) — batch as hardening; F9b's assert and F9a's one-liner are trivial; F8's metrics are additive.

Rationale: lead with the small High-severity, self-contained fixes (F1, F4) that stop active corruption, then the medium-effort High availability/safety fixes (F5, F2-L1), defer the one invasive structural change (epoch fence) until it can pay for F2/F7/F9b together, and sweep the Low items last.

## 4. Did the review miss anything?

The original review was strong; the verifiers surfaced several real gaps the original doc did NOT flag. The additional risks worth recording:

1. **The empty-content blob as the universal hot row (F6).** The original picked `package-lock.json`; the sha256-of-zero-bytes blob is hotter (every `touch`/`>`/empty write) and routes through the identical end-of-tx tuple lock. This is a meaningfully larger contention surface than the chosen example.
2. **No `lock_timeout`/`statement_timeout` anywhere (F6).** The original (and investigators) assumed "up to a minute"; in fact a contender blocks indefinitely (bounded only by holder/lease/`max_lifetime`). Combined with the `max=2` PG pool, this is a fleet-wide pool-exhaustion → 503 path the review did not name.
3. **`publishPending` and the F3 heal are non-durable across reap.** The original treated "next write heals it" as a guarantee; the verifier showed reap-before-next-write **permanently discards** the pending bump. The `Session.publishPending` doc-comment (`199-207`) asserts a guarantee the code does not provide — a documentation bug the review missed.
4. **The "never-written" F7 variant (zero-write session).** The original's F7 trace assumed a reload-to-empty; the silent-ghost variant (`0===0`, no reload, serves a populated cache against a deleted sandbox) is arguably worse and is NOT fixed by a loadAllPaths-empty guard alone.
5. **F7's true observable is a 200-with-garbage-exit, not a 404.** The review framed it as "bewildering ENOENTs / no clean 404"; the dominant surface is an HTTP 200 exec with non-zero exit + garbage stderr — worse for clients than a 404.
6. **F2's mechanism (the most material miss).** The original's tx1/tx2 interleaving is impossible in the exec path; had the review's fix-(3) ("make appendFile single-transaction") been shipped, it would have been a no-op against a real bug. The actual mechanism — in-memory base capture + content-addressed read — is what the epoch fence must target.
7. **Stale `ownership.ts:60-66` docstring (F5).** Claims readOnly takes no distributed lock; it does. A reader trusting that comment would mis-reason about outage blast radius.
8. **F4's deeper root cause and divergent-cache harm.** The review over-weighted the lost-INCR; the silent divergent-cache (wrong `stat`/`readdir`/`readFile` until next reload, because `endScriptScope` success path never rebuilds `#pathCache`) is the more robust harm and survives even when `#dirty` is later re-armed.
9. **Cross-replica-only nature of F9d.** Not a miss of existence but of framing — it is unreachable until multi-replica-same-sandbox traffic exists, which the rehydration work deliberately enables; the review treated it as generic.

No *additional* correctness flaw beyond F1–F9 surfaced in my own read. The most consequential omissions are #2 (unbounded blob-lock wait + pool exhaustion) and #6 (F2 mechanism), both of which change the recommended fix rather than the verdict.
