# Verdict

Verdict: redesign before implementation. Host-side extraction and wheel-SHA reuse address verified bridge and duplicate-write costs, but the proposed ZIP parser, per-entry staging moves, and manifest GC root are not safe enough as written (`node_modules/just-bash/dist/bundle/chunks/worker.js:1609-1617`, `src/sql-fs/sql-fs.ts:1400-1405`, `thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:601-609`). The redesign needs an atomic publish operation, an authoritative installed-package ledger, a GC-safe manifest transaction, and a supported construction for pip-scoped fetch before implementation starts (`src/api/session-manager.ts:1645-1666`, `src/sql-fs/migrations/postgres/0000_create_tables.sql:16-25`, `node_modules/just-bash/package.json:16-31`).

# Design challenges

## Host-side unzip

Moving extraction out of the WASM worker is the correct boundary because the worker reads a file through one 8 MB result buffer and writes each extracted file twice (`node_modules/just-bash/dist/bundle/chunks/worker.js:1609-1617`, `node_modules/just-bash/dist/bundle/chunks/worker.js:2285-2294`, `node_modules/just-bash/dist/bundle/chunks/worker.js:2329-2371`). The proposed synchronous parser is not acceptable in the API process as specified: the plan limits itself to selected ZIP64 size fields and central-directory sizes, then uses `inflateRawSync` (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:480-495`), while synchronous zlib work blocks further JavaScript execution according to the [Node zlib documentation](https://nodejs.org/api/zlib.html#class-options).

The existing extractor rejects empty, absolute, backslash-containing, overlong, dot-segment, duplicate, and symlink paths, and it enforces cumulative file and declared-byte limits before writing (`src/api/commands/pip-command.ts:48-80`). A replacement also needs to reject NULs, central/local-header disagreement, overlapping or out-of-bounds regions, ambiguous filename encodings, directory/file path collisions, unsupported file kinds, descriptors it does not implement, and malformed EOCD/ZIP64 structures. CRC verifies accidental corruption, while the wheel SHA authenticates the downloaded archive against PyPI metadata; neither makes the parser memory-safe or proves that the installed layout follows the wheel standard (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:488-495`).

The plan also treats every archive path as a site-packages path, but the wheel specification requires parsing `WHEEL`, checking `Wheel-Version`, and spreading `.data/(purelib|platlib|scripts|data)` subtrees to their destinations ([PyPA wheel installation](https://packaging.python.org/en/latest/specifications/binary-distribution-format/#installing-a-wheel-distribution-1-0-py32-none-any-whl)); the current extractor likewise joins every entry directly to one destination (`src/api/commands/pip-command.ts:71-79`). **Recommendation: keep host-side extraction, but replace the hand-written synchronous parser with a maintained, fuzz-tested ZIP reader behind an async/worker boundary, validate both ZIP headers and RECORD hashes, and explicitly implement or reject every wheel layout outside the supported subset.**

## Manifest key and GC root

Wheel SHA-256 is a stronger identity than `(name, version)` because the selected artifact already carries a PyPI SHA and current code verifies it before extraction (`src/api/commands/pip-command.ts:640-650`, `src/api/commands/pip-command.ts:847-850`). Normalized child rows make path validation and blob anti-joins explicit, and the proposed `blob_sha256` index supports the equality probe used by the new anti-join (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:601-609`). Add an installer-format version to the parent key or row so a future change in path spreading, mode normalization, or compatibility overlays cannot reuse an old interpretation of the same archive.

The proposed child table has no foreign key to `blobs` (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:601-609`), while the current schema also has no FK from inode content hashes to blobs (`src/sql-fs/migrations/postgres/0000_create_tables.sql:16-25`, `src/sql-fs/migrations/postgres/0000_create_tables.sql:38-44`). Current GC correctness depends on a concurrent adopter touching the blob before adding its inode so REPEATABLE READ turns the update/delete conflict into a retry (`src/api/blob-gc.ts:30-58`, `src/sql-fs/dialects/postgres.ts:740-766`). Recording only manifest rows creates no conflict on the blob row, so GC can delete a blob from its snapshot while a concurrent install records the new manifest reference.

The TTL prose is also off by one pass: deleting expired parent rows before the blob anti-join in the same transaction makes their blobs eligible in that same statement snapshot, not only on the next scheduled pass (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:618-627`). **Recommendation: add `package_manifest_files.blob_sha256 REFERENCES blobs(sha256) ON DELETE RESTRICT`, touch or lock all referenced blob rows and insert the manifest in one transaction, retry serialization failures, include a manifest-format version, and state that expired roots can be collected in the same GC pass.**

## Staging and publication

SqlFs `mv` uses `mvComposite` inside `#withBareTx`, so it joins an active script transaction, and its cache update remaps the subtree rather than copying file bytes (`src/sql-fs/sql-fs.ts:1407-1447`, `src/sql-fs/sql-fs.ts:314-332`). That does not make the proposed publication algorithm work: moving a staged top-level directory onto an existing non-empty package directory throws `ENOTEMPTY` (`src/sql-fs/sql-fs.ts:1400-1405`). Multiple top-level moves are atomic only while one script transaction remains open; a resolved exit-code-1 result still commits, and a plain timeout also follows the commit path unless the distributed lock itself was lost (`src/api/session-manager.ts:1649-1666`).

A database connection loss rolls back the open transaction, but a process crash before opening it can leave hidden staging entries, and a crash or timeout during publication must not rely on command-result cleanup (`src/sql-fs/sql-fs.ts:279-311`, `src/api/session-manager.ts:1650-1666`). Calling `abortScriptScope` for every nonzero shell result would change the transaction semantics of all commands, so that is wider than this installer needs (`src/sql-fs/session-scoped-fs.ts:22-35`). **Recommendation: add one dialect-level `publishPackageInstall` transaction that merges staged file dirents, removes superseded owned paths, updates the authoritative installed ledger, and deletes staging in one commit; add an age-based cleanup for abandoned staging roots.**

## Existence-aware bulk ingestion and cache policy

Passing `presentBlobs` from the installer to `bulkIngest` is unsafe because inode creation can then trust a stale positive result, and a missing blob is currently read as an empty file (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:500-509`, `src/sql-fs/sql-fs.ts:1185-1189`). The dialect interface currently makes `bulkIngest` required but makes the special self-committing blob optimization optional (`src/sql-fs/types.ts:308-322`, `src/sql-fs/types.ts:391-396`). The new behavior is a correctness protocol, not an optimization, so an optional method with a caller-computed set is the wrong abstraction.

Skipping all content-cache population avoids eviction during installation, but every later module miss reaches the blob read path, which only caches after reading (`src/sql-fs/sql-fs.ts:1169-1189`). Snapshot rehydration can prefetch Redis blobs only when both snapshot and blob cache are configured (`src/sql-fs/sql-fs.ts:592-609`), and Redis itself skips blobs above its maximum (`src/sql-fs/redis-blob-cache.ts:82-86`). **Recommendation: make a required dialect operation own missing-hash detection, touches, payload insertion, and inode creation; cache only a bounded set of small `.py` and metadata files after commit, then benchmark cold and warm `databricks` startup before fixing the policy.**

## Singleflight and lock ordering

The stated wheel-by-wheel flow acquires and releases one lease before moving to the next wheel (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:342-355`). That order does not create the proposed X/Y deadlock because a sandbox does not hold X while waiting for Y, although its per-sandbox exec lock remains occupied while it waits. The more serious issue is lease correctness: a bare fixed 120-second `SET NX PX` can expire during a slow install, and the plan explicitly accepts racing after expiry (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:653-659`, `thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:736-738`).

The repository already has token ownership, renewal, compare-and-delete release, and a lost-ownership signal (`src/api/distributed-lock.ts:1-8`, `src/api/distributed-lock.ts:20-32`, `src/api/distributed-lock.ts:127-183`). The manifest must be committed and visible before lease release; recording all manifests only after all wheels succeeds conflicts with wheel-scoped singleflight and lets a failed multi-wheel install waste already completed reusable work (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:629-635`). **Recommendation: reuse the existing renewable distributed-lock primitive per wheel, commit each validated wheel manifest before releasing that wheel's lease, and preserve a documented duplicate-work fallback when Redis is absent.**

## Install and Python concurrency

A default of two bounds only the code wrapped by that semaphore. The plan acquires it around one wheel's download and extraction, so dependency metadata resolution and installations waiting between wheels remain outside the cap (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:423-428`). Its 160 MB estimate counts two wheel buffers, secure-fetch assembly copies, 8 MB inflate batches, and 8 MB driver buffers, but excludes parser structures, SQL parameter copies, path/hash arrays, concurrent metadata bodies, Redis writes, and synchronous inflate stalls (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:533-539`).

Adding `databricks` to the script regex catches common invocations but remains a heuristic over shell source, as the plan itself notes (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:429-432`). The actual Python execution happens at `ctx.exec("python")`, below command dispatch (`src/api/commands/pip-command.ts:792-800`, `src/api/commands/pip-command.ts:957-960`). **Recommendation: acquire pip capacity for the whole install orchestration, use async decompression or a bounded worker pool, cap cumulative metadata fetches separately, and place Python capacity at the actual built-in Python call rather than expanding the outer regex.**

## Revised limits and path-cache budget

The path budget is not a fixed 150 bytes per entry: the implementation charges `path.length + 100`, sets `overBudget` above 50 MB, and the reaper removes any idle session marked over budget (`src/api/session-manager.ts:447`, `src/api/session-manager.ts:528-541`, `src/api/session-manager.ts:650-665`, `src/api/session-manager.ts:1503-1514`). At the plan's assumed 50-character average path, 50 MB permits about 349,525 entries, so its 350,000 approximation is reasonable for that assumption. A 1 GB byte quota does not bound path count, and `50,000 files per install` allows repeated installs to exhaust the path budget while staying far below 1 GB (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:518-531`).

The proposed quota reads totals from `/site-packages/.sqlfs-installed.json`, a file in the same caller-writable filesystem used for package data (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:567-582`, `src/sql-fs/sql-fs.ts:850-913`). It therefore cannot be an authoritative quota or ownership ledger. Every dirty publish can also serialize the full path cache into one Redis msgpack value (`src/api/session-manager.ts:1111-1116`, `src/sql-fs/redis-path-snapshot.ts:87-109`). **Recommendation: enforce independent authoritative per-sandbox byte and path-count limits in PostgreSQL, reserve headroom for user files, cap or disable oversized path snapshots, and expose the JSON record only as a derived compatibility view.**

## Credential handling

Per-request environment credentials avoid filesystem persistence and current redaction reads the Databricks values from command context (`src/api/commands/pip-command.ts:927-939`). A config file written through SqlFs commits its bytes to the shared CAS, can populate the session LRU, and can be copied to Redis when enabled and at or below the cache threshold (`src/sql-fs/sql-fs.ts:856-913`, `src/sql-fs/dialects/postgres.ts:615-633`, `src/sql-fs/redis-blob-cache.ts:82-86`). The default MCP export root is `/home/user`, so a conventional config there is included when the caller exports that root (`src/api/mcp/tools.ts:526-575`).

The plan's minimum redaction length is useful, but documentation alone does not protect users who choose a config file (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:385-413`). **Recommendation: keep request env as the default, document config files as persistent/exportable secrets, redact configured token values when a config path is explicitly supplied, and add an export option that excludes known credential paths by default.**

## Write methods in the requests shim

Removing the GET/HEAD check is a security regression in the guardrail provided to ordinary Databricks CLI use, even though it is not a complete sandbox boundary. The shim currently rejects other methods (`src/api/commands/pip-command.ts:283-287`), while the Bash network configuration grants full outbound access when network is enabled (`src/api/session-manager.ts:605-613`). SECURITY.md currently promises that the compatibility transport supports only read-only methods and rejects unsupported methods (`SECURITY.md:99-104`), while separately warning that sandbox code can make any request allowed by the transport (`SECURITY.md:111-121`).

Allowing write methods by default would make the documented claim false and increase the chance that unmodified agent code mutates a workspace. **Recommendation: retain read-only methods as the default, add an explicit per-sandbox or per-exec write-method capability, enforce it at the fetch transport as well as the requests shim, and update SECURITY.md to distinguish a guardrail from a malicious-code boundary.**

# Missed issues

## The installed record is mutable and cannot establish ownership

The plan derives quota totals and uninstall file lists from `/site-packages/.sqlfs-installed.json` (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:571-582`). Any sandbox command can write ordinary files through SqlFs (`src/sql-fs/sql-fs.ts:850-913`), so the same principal being limited can lower those totals, remove another package's paths from the list, or add user paths to a package's uninstall list. Proposed plan change: store package/version, owned paths, content hashes, and totals in sandbox-scoped PostgreSQL tables updated by the atomic publish transaction; generate the JSON file from that state if compatibility needs it.

## Shared paths make uninstall and upgrade destructive

The plan says uninstall removes exactly one package record's file list and upgrade removes old-version files before publication (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:357-359`, `thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:571-576`). It also expects multiple wheels whose path sets may contain identical-content files (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:639-643`). A flat file list does not say whether another installed distribution still owns a shared path or whether the current bytes still match the installing package. Proposed plan change: add per-path ownership and installed content hashes, reject conflicting non-identical ownership at install time, and delete a path only when no remaining owner exists and its current hash still matches the ledger.

## The resolver admits some development releases and misorders PEP 440 forms

The parser stores `dev` separately from `pre`, but prerelease filtering checks only `.pre` (`src/api/commands/pip-command.ts:523-555`, `src/api/commands/pip-command.ts:721-726`). The comparator handles prerelease, post, and dev fields in a custom order, and normalized matching omits the dev suffix (`src/api/commands/pip-command.ts:558-590`). Proposed plan change: either adopt a tested PEP 440 implementation or define a narrower supported version grammar and reject unsupported releases; add dev, post, local, epoch, wildcard, and compatible-release conformance fixtures before expanding package support.

## Marker evaluation is incomplete and Phase 0's fallback is unsafe

The environment omits standard fields including `platform_release`, `platform_version`, and `implementation_version` (`src/api/commands/pip-command.ts:443-454`). The proposed change turns any unknown variable into false (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:433-435`), which silently drops a dependency instead of making the release ineligible or surfacing a diagnostic. Current `in` handling also splits the right operand on commas (`src/api/commands/pip-command.ts:466-479`), while the packaging specification defines string containment and requires the standard marker fields ([PyPA dependency specifiers](https://packaging.python.org/en/latest/specifications/dependency-specifiers/#environment-markers)). Proposed plan change: implement all required marker values and comparison semantics, then treat an actually unknown field as a resolver diagnostic or an ineligible release, never as a silently unsatisfied dependency edge.

## Dependency-depth accounting can be bypassed

The resolver stops processing a package when the selected version is unchanged before it propagates dependencies using a newly increased depth (`src/api/commands/pip-command.ts:770-786`). A package first reached by a shallow path and later reached by a deeper path can therefore retain descendants that were never checked at the deeper depth. Proposed plan change: model the dependency graph explicitly, recompute maximum reachable depths when an edge is added, and test a diamond graph whose second path pushes an existing subtree over the configured limit.

## Metadata has no install-wide byte or request budget

Each JSON response has a per-response check and successful responses remain in the resolver cache (`src/api/commands/pip-command.ts:672-713`). Candidate inspection can fetch per-version JSON repeatedly, bounded by a candidate counter but not by cumulative metadata bytes (`src/api/commands/pip-command.ts:716-742`). Raising the response limit to 16 MB increases the possible aggregate retained memory (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:439-441`). Proposed plan change: add cumulative metadata-byte, request-count, and cached-entry limits per install, and include them in the global pip admission budget.

## The synthetic requests package is too broad

The plan proposes treating every `requests` requirement as satisfied and skipping its dependencies (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:400-405`). The compatibility package implements only the surface needed by the current experiment and patches request dispatch (`src/api/commands/pip-command.ts:95-306`). Proposed plan change: activate synthetic requests only for a tested Databricks CLI compatibility profile, record its synthetic version/capabilities, and fail other packages whose requests constraints or imported API exceed that profile.

## Manifest reuse needs an installer-format version and RECORD verification

The proposed manifest identity contains the archive SHA, package name, version, and file rows, but no version of the extraction/install algorithm (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:588-609`). The plan verifies ZIP CRC but does not require validating every installed file against `.dist-info/RECORD` (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:488-495`), while the wheel specification requires every file except the RECORD/signature exceptions to be listed and hash-verified ([PyPA RECORD rules](https://packaging.python.org/en/latest/specifications/binary-distribution-format/#the-dist-info-directory)). Proposed plan change: version the normalized manifest format and reject wheels whose RECORD set or SHA-256 hashes do not match the normalized installed file set.

## Path snapshots are updated, but their full-value cost is missing

`bulkIngest` marks SqlFs dirty after updating its path cache (`src/sql-fs/sql-fs.ts:823-837`), and session finalization writes a fresh snapshot when the filesystem is dirty (`src/api/session-manager.ts:798-816`, `src/api/session-manager.ts:1061-1128`). There is no stale-snapshot correctness bug in that path. The scalability issue is that every publish encodes the entire path cache into one Redis value, with no size check in the writer (`src/sql-fs/redis-path-snapshot.ts:87-110`). Proposed plan change: add snapshot byte/entry caps and an acceptance test for a large graft, with a database-reload fallback when the cap is exceeded.

## No-Redis multi-replica behavior remains duplicate work

The plan's fallback map gives singleflight only within one replica (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:653-659`). PostgreSQL CAS prevents duplicate stored blob rows, but both replicas still download, inflate, hash, and transmit the same payload before `ON CONFLICT` resolves it (`src/sql-fs/dialects/postgres.ts:1014-1033`). Proposed plan change: state this limitation explicitly and either accept it as the no-Redis operating mode or add a PostgreSQL advisory lock keyed by wheel SHA for cross-replica singleflight.

## Export analysis in the plan is stale

The handoff names a tar.gz export under `routes/ingest.ts`, but that route only implements JSON ingest (`src/api/routes/ingest.ts:15-94`). Current export is the MCP `fs_export` JSON map, defaults to `/home/user`, and includes every descendant of an explicitly supplied base path subject to count and byte limits (`src/api/mcp/tools.ts:526-575`). `/site-packages` is outside the default root but is exportable if a caller chooses `/` or `/site-packages`. Proposed plan change: replace the stale export note with the current MCP behavior and decide whether an explicit `includePackages` option should be required for package trees.

## A just-bash 3.4.2 upgrade changes fixes, not the bridge conclusion

The 3.4.2 fork adds `stdin` and `maxFileSize` to `WorkerInput`, passes stdin and the configured string limit, redirects `io.open_code` for `runpy`, and maps cancellation to exit 124 (`/Users/nguyendangquang/master/Web-Dev/just-bash/packages/just-bash/src/commands/python3/worker.ts:27-38`, `/Users/nguyendangquang/master/Web-Dev/just-bash/packages/just-bash/src/commands/python3/worker.ts:835-846`; `/Users/nguyendangquang/master/Web-Dev/just-bash/packages/just-bash/src/commands/python3/python3.ts:474-521`, `/Users/nguyendangquang/master/Web-Dev/just-bash/packages/just-bash/src/commands/python3/python3.ts:614-623`). It still uses an 8 MB bridge buffer and still reads the entire file before setting the protocol result (`/Users/nguyendangquang/master/Web-Dev/just-bash/packages/just-bash/src/commands/worker-bridge/protocol.ts:95-104`, `/Users/nguyendangquang/master/Web-Dev/just-bash/packages/just-bash/src/commands/worker-bridge/bridge-handler.ts:227-235`). Proposed plan change: split Phase 0 fixes into 3.0.1-only and still-needed-after-3.4.2 groups, test both dependency choices, and keep host extraction regardless of upgrade.

# Open questions for the user

1. **ZIP implementation ownership.** Options: accept a maintained ZIP dependency and audit its limits, or own a custom parser isolated in a worker with a fuzzing and maintenance budget. Recommendation: accept the dependency; the current plan otherwise puts a new untrusted binary parser in the API process (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:727-735`).

2. **No-Redis duplicate work.** Options: accept duplicate first-install work across replicas, or use a PostgreSQL advisory lock keyed by wheel SHA. Recommendation: accept duplication initially if no-Redis is a development/degraded mode; choose the advisory lock if it is a supported production topology (`thoughts/shared/plans/2026-09-18_12-44-19_cross-sandbox-package-reuse-v2.md:653-659`).

3. **User-modified package files on upgrade/uninstall.** Options: preserve modified files and report them, fail the operation pending `--force`, or delete them. Recommendation: preserve and report by default, with an explicit force path; a content hash is available in the proposed ownership ledger (`src/api/commands/pip-command.ts:847-850`).

4. **Databricks write methods.** Options: keep the product read-only, permit writes through an explicit per-exec/per-sandbox capability, or permit writes whenever network is enabled. Recommendation: explicit capability, because the current user-facing contract says the compatibility transport is read-only while the underlying network capability is broader (`SECURITY.md:99-115`).

5. **Package export semantics.** Options: never export site-packages, export it only with `includePackages`, or preserve the current arbitrary-base-path behavior. Recommendation: require `includePackages` and exclude known credential files by default; current export is a general descendant walk under the requested base path (`src/api/mcp/tools.ts:526-575`).

6. **just-bash baseline.** Options: implement against pinned 3.0.1 first, upgrade to 3.4.2 before this work, or support both during rollout. Recommendation: upgrade first if the fork is releasable, then delete the 3.0.1-only stdin/path work while retaining host extraction and bridge-limit tests (`/Users/nguyendangquang/master/Web-Dev/just-bash/packages/just-bash/src/commands/python3/worker.ts:27-38`, `/Users/nguyendangquang/master/Web-Dev/just-bash/packages/just-bash/src/commands/python3/worker.ts:835-846`; `/Users/nguyendangquang/master/Web-Dev/just-bash/packages/just-bash/src/commands/worker-bridge/protocol.ts:95-104`).
