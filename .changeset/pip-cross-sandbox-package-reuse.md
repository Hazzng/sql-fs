`pip install` now runs on the host and reuses wheels across every sandbox in the tenant, and packages have a real ledger: `pip uninstall`, `pip list` and `pip freeze`.

Installing used to hand the wheel to CPython in the sandbox, which capped a wheel at the 8 MB WASM bridge buffer and re-downloaded and re-stored the same bytes for every sandbox. A wheel is now read in the API process with `yauzl`: the whole central directory is validated before the first byte is inflated, every entry is inflated asynchronously in bounded batches with `maxOutputLength` set to its declared size, and each entry's CRC-32 and `RECORD` SHA-256 are checked. Verified bytes are committed as content-addressed blobs and recorded in a tenant-global manifest; the sandbox tree changes in one DB-only graft at the end, so a failed install publishes nothing. The first install of a wheel anywhere in the tenant downloads it once — with `REDIS_URL` set, once fleet-wide, behind a per-wheel lease — and every later install, in any sandbox, is a manifest lookup plus the graft. Measured against real PyPI: `databricks-cli` and its seven dependencies took 1852 ms into a cold sandbox and 182 ms into the next one, with zero downloads.

`pip uninstall NAME` removes the ledger row and the paths that wheel alone owns whose content still matches the manifest; a file you edited is preserved and reported rather than deleted. `pip list` and `pip freeze` read the ledger. Quotas (`PIP_SANDBOX_QUOTA_BYTES`, `PIP_SANDBOX_MAX_FILES`) are enforced from those rows in Postgres before anything is written, not from a file the sandbox can edit — files left under `/site-packages` by an install that predates the ledger are outside the quota until the package is installed again.

Sandboxes gain an opt-in `networkWrite` flag (create body and MCP `sandbox_create`, requires `network: true`): it exports `SQLFS_HTTP_WRITE=1` and lets the Python `requests` compatibility shim issue POST, PUT, PATCH and DELETE. Without it those verbs raise `NetworkWriteNotPermitted`. It is a guardrail inside the shim, not a transport restriction — `curl`, `jb_http` and `git` are unaffected, and SECURITY.md now says so plainly.

Also in this release: the resolver handles extras, the full PEP 508 marker variable set (an unknown variable is a hard error rather than a silently dropped edge), correct PEP 440 dev-release ordering, and cumulative per-install metadata caps; `python3` / `python` overrides fix script-path translation, stdin and interpreter-option parsing; PyPI traffic goes through a GET-only fetch pinned to `pypi.org` and `files.pythonhosted.org`; installs are admission-controlled by `MAX_CONCURRENT_PIP_INSTALLS` (default 2) and take a Python slot only where a CPython worker is actually spawned. Every size limit lives in one place and every refusal names its knob: `PIP_MAX_WHEEL_BYTES`, `PIP_MAX_INSTALL_DOWNLOAD_BYTES`, `PIP_MAX_FILE_BYTES`, `PIP_MAX_INSTALL_BYTES`, `PIP_MAX_INSTALL_FILES`, `PIP_SANDBOX_QUOTA_BYTES`, `PIP_SANDBOX_MAX_FILES`, plus `REDIS_PATH_SNAPSHOT_MAX_BYTES` for oversized path snapshots.

Operationally: migrations `0007` (package manifests, manifest files, `sandbox_packages`) and `0008` (`sandboxes.network_write`) apply on boot. `pnpm db:gc` now sweeps expired package manifests before the blob anti-join in the same transaction and reports `manifestsDeleted` — manifests are a GC root, so a wheel's blobs live as long as its manifest, for `PIP_MANIFEST_TTL_MS` (default 30 days) after nothing references it. `pip install` emits `pip_manifest_hit` / `pip_manifest_miss` / `pip_singleflight_wait` / `pip_publish` log lines with file counts, bytes and elapsed time. The unused `drizzle-kit` scaffold is gone: `pnpm db:generate`, `drizzle.config.ts`, the drizzle dependencies and the now-unreferenced `DATABASE_DIRECT_URL` were removed, since Postgres migrations have always been hand-written SQL applied on boot.
