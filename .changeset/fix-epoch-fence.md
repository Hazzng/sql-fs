Fence a writer whose lease lapsed, so a replica that has lost the exec lock can no longer silently destroy the write of the replica that took it over.

**The bug, precisely.** `appendFile` takes its base from the in-memory pathCache (`existing.contentSha256`) **before any lock is held**, and `getBlob` is content-addressed — it reads by hash, so it keeps serving that base long after another replica replaced the dirent. A writer A whose Redis writer key expired therefore rebuilds `stale-base + append` and points the dirent at the result, erasing B's committed line. `pg_advisory_xact_lock` cannot stop it: the lock serializes the transactions, but the read it would need to fence was already taken, in memory, before the lock existed. The heartbeat cannot stop it either — `markLost()` only fires on the renew timer, so any request that starts and finishes inside one interval (20 s by default) commits without consulting a lease it no longer holds. Reproduced 7/7 on the two-replica harness: both replicas exit 0, one committed write gone, verified against the `blobs` table.

**The fix.** `sandboxes` gains `version BIGINT NOT NULL DEFAULT 0` (migration `0007`), read in the same call that loads the pathCache and pinned as the writer's epoch. Every composite write (`writeFileComposite`, `mkdirComposite`, `rmComposite`, `mvComposite`) now carries that pin into an `UPDATE sandboxes SET version = version + 1 WHERE id = $s AND version = $expected` inside its advisory-locked `ctx` CTE, and **every** mutating CTE in the statement reads from that fence — directly, or through `new_inode` / `old_dirent`, which is cross-joined with it. A stale pin therefore matches zero rows and the statement writes nothing at all; gating only the INSERTs would still run `deleted_old_inode` and drop the live writer's inode, cascading its dirent away. The epoch advances in memory in lockstep, so later writes in the same transaction match the row the first one already bumped, and a rollback re-reads it from Postgres.

**Committing was the other half of the hole.** A fenced CTE matches zero rows; it does not raise. The transaction stays perfectly committable, and bash swallows a failed command in a script without `set -e` — so `endScriptScope` would have COMMITted and answered 200/exit 0 for a script whose writes were all dropped, which is the same silent success in different clothing. The verdict is now sticky for the scope: every later operation fails and `endScriptScope` rolls back instead of committing.

**What a client sees.** A new code `ESTALEEPOCH` → **503, `retryable: true`**. The fenced statement wrote nothing and the transaction was rolled back, so a retry — which reloads the cache and re-runs against the live epoch — is both safe and the way forward. On the harness the zombie replica now answers `503 ESTALEEPOCH` and the takeover replica's line survives, on both replicas and in the `blobs` table.

**Cost.** One extra row UPDATE per composite write, in the same statement (no extra round trip), plus one `SELECT version` per cache load (cold start and reload — not per exec). Measured on the load harness at concurrency 1 over a 40/25/20/15 read/write/exec/edit mix: ~577 → ~478 ops/s, about **17%**, narrowing to under 10% by concurrency 8. The real cost is that `sandboxes` now has one hot row per sandbox: every write rewrites it, so that row accumulates dead tuples at write rate and depends on autovacuum to stay small. A long-running script transaction also now holds a row lock on `sandboxes` for its whole duration, so DDL against that table (a migration during a rolling deploy) waits behind it where it previously did not.

**Rolling deploys.** The column is backward compatible in both directions: `createSandbox` inserts with an explicit column list and nothing selects `*`, so a replica that predates the migration runs unchanged against a migrated database — it simply never bumps the counter, and is neither fenced nor fencing. Protection is therefore only complete once every replica is on the new code; until then the mixed fleet behaves exactly as it does today.

**Not covered.** Only the four composite writes are fenced. `bulkIngest`, `mkdir -p`, `rm -r`, `cp`, `link`, `symlink`, `chmod`, `utimes` and `truncate` still mutate through the non-composite path, so they neither advance the epoch nor are fenced by it — a zombie doing only those can still lose an update, exactly as before. Sandbox delete-and-recreate reuses id `0`, so a scope pinned at epoch 0 against a deleted sandbox would pass the fence of its replacement; that is the tombstone half of #136 and is deliberately out of scope here.

Verified against a real Postgres (7 integration tests, including one that swallows the fence error and COMMITs anyway to prove the SQL alone destroys nothing) and 14 unit tests; every one was checked by reverting its source change in isolation — including each individual CTE gate — and confirming the failure. The load-test harness's `concurrency.mjs` stays all-PASS.
