Stop a dying Postgres connection from killing the replica, and make the request it belonged to fail instead of hang.

**The replica died, 3/3, with no admin command.** `ALTER DATABASE … SET idle_in_transaction_session_timeout = '1500ms'` plus `echo a > /f1.txt; sleep 3; echo b > /f2.txt` is enough. A script scope pins one backend `idle in transaction` for the whole duration of arbitrary user bash, so any `sleep`, Python step or network fetch is long enough for the backend to be reaped. `postgres.js` then nulls that connection's socket in `closed()` while a write for it is still buffered, and flushes the buffer from a bare `setImmediate`:

```
TypeError: Cannot read properties of null (reading 'write')
    at Immediate.nextWrite (…/postgres@3.4.9/…/postgres/src/connection.js:255:22)
    at process.processImmediate (node:internal/timers:505:21)
```

There is no promise and no `try` between that frame and the event loop, so it is a fatal uncaught exception. One unlucky script takes the whole replica down and with it every other in-flight request on it — and on a pooler, where `idle in transaction` backends are precisely what gets reaped, that is a crash-loop shape rather than a one-off. The sibling synchronous path is the one #169 names: `execute`'s catch at `connection.js:179` calls `write(Sync)` on the very socket whose error it is handling, which escapes as an unhandled rejection through `Query.handle`.

**The guard is one stack frame wide, and the tests keep it that way.** A blanket `uncaughtException` swallow would hide every real bug in the process, so the recogniser requires a `TypeError` *and* a stack frame naming `nextWrite` inside `postgres/src/connection.js` — a private driver helper no other code in the process can appear in. It does not match on the message ("Cannot read properties of null" is V8-version specific) or on the line number (it moves between driver releases). Everything else — including a `TypeError` with the identical message thrown from our own code, and an unrelated unhandled rejection — keeps Node's default: the handlers detach and the error is re-thrown on the next tick, so the stderr dump and the exit code are the real default path rather than an approximation of it. Three of the five child-process tests are negative guards asserting exactly that, and they fail if the recogniser is widened to a blanket match.

**Suppressing the crash alone would have been a downgrade, not a fix.** The driver throws *instead of* rejecting the query it was writing, so that query's promise never settles — not on connection close (that handler already ran), and not on the exec timeout's `AbortSignal`, because the await is not abortable. #169 measured this directly: with the crash suppressed by a preload harness the request hung until the client gave up at 120 s with nothing committed. So every SqlFs await on the driver now arms a grace window when a fault fires and fails with `EDRIVERFAULT` → **503, not retryable** if it is still pending when the window closes. Not retryable because the fault can land on a connection that already had its `COMMIT` on the wire: "nothing was applied" is exactly what cannot be proved here, the same reasoning as `ECOHERENCE`. Inside a script scope the verdict is sticky, like `#scriptTxLost` — the rest of the script fails closed rather than reopening on a connection that is at best suspect and committing half of it.

**A condemned scope must not commit, and must not keep writing.** Three gaps let one do both. `endScriptScope` never looked at `#scriptTxLost`: after a fault every later fs op throws through `#assertScriptTxAlive`, but just-bash swallows those into a nonzero exit rather than rejecting, so the exec path still reached `endScriptScope` — which COMMITTED whatever part of the script had landed and answered success. It now routes through the existing abort path (reject `endPromise` → ROLLBACK → reload) and rethrows the fault. `writeFile`/`appendFile` awaited `commitBlob` — a root-`sql` statement on the reconnected connection — *before* `#withBareTx` reached the liveness assert, so a write in a condemned scope still put a statement on the wire; the assert now runs first, and the call goes through the same raced helper as everything else, so a fault during the blob write cannot leave it pending either. `loadAllPaths` and `#refreshKnownEpoch` were likewise unraced (and outside the defense-in-depth escape hatch) and now go through it too. Boot migrations had the same shape at the worst possible moment: unraced, a fault during `runMigrations` used to exit 1 and let the orchestrator restart, and with the guard installed it would instead hang forever without ever reaching `listen` — no health check to fail, no restart, no log line after startup.

**The grace window is why healthy queries survive.** A process-level handler cannot tell which connection the dropped write belonged to, so waking every waiter the instant a fault fires would fail concurrent statements on healthy connections — and a statement failed while it is still on the wire may commit anyway, which is the applied-but-reported-failed shape this whole stack exists to remove. `PG_DRIVER_FAULT_GRACE_MS` (default 5000) keeps the blast radius to awaits that are never going to settle: a healthy statement finishes in milliseconds, a dropped one finishes never. The timer is `unref`'d, so a fault can never hold a draining process open.

**Cost: a logged fault instead of a restart, and some operators will not want that trade.** After this change a driver fault is an `event:"driver_socket_fault"` line on stderr carrying the driver's message, stack and the waiter count, plus one or more 503s — and the replica keeps serving from a pool that just lost a connection. That is worse than a restart in one specific way: the loud, unmissable signal becomes a log line, so a deployment that alerts on restarts but not on log events goes quiet about a fault it used to page for. It is better in every other way. A crash drops every concurrent request, including reads that never touched the dead connection; `postgres.js` reconnects the pool entry on the next query, so there is nothing about a single dropped socket that makes the *process* unsound; and a restart costs every warm session on the replica, which means a cold `loadAllPaths` for each on the next request. Alert on `driver_socket_fault`. Operators who genuinely prefer the crash — fast orchestrator restarts, restart-based alerting, a policy of not serving from a degraded pool — set `PG_DRIVER_FAULT_GUARD=false` and get the old behaviour back exactly.

Verified against the live FAULT load-test replica: **crashed 3/3 before** (`HTTPCODE=000`, pid gone, the `TypeError` above as the last line of `fault.log`), **survived 3/3 after** — same pid throughout, HTTP 500 in ~3.0 s, and `f1`/`f2`/`f3` all 404, so nothing was torn. `concurrency.mjs` stays all-PASS, exit 0. The `idle_in_transaction_session_timeout` override was reset afterwards. Every new test was checked by reverting the source change and confirming it fails; the process-level tests are child processes on purpose, because vitest installs its own `uncaughtException` handler and an in-process assertion about a crash passes with or without the fix — the same trap that let an earlier crash test in this repo pass with its fix removed.

**Not verified, and one thing worth knowing.** The grace-window arm never actually fired in the live reproduction: all three runs logged `"waiters":0`, meaning no SqlFs await was pending on the dropped query at that instant, and the 500 came from the existing fail-closed script-tx guards (`52cc836`, `d78ba26`), which already bound this particular path. The hang #169 reports is therefore no longer reproducible on this branch — confirmed by re-running the reproduction with the race disabled, which still answered 500 in 3.0 s. The arm is kept because it is the only mechanism that can end a wait on a query the driver dropped, and nothing guarantees that the query the driver drops is never one we are awaiting; but it is defence rather than a demonstrated cure, and it is exercised by unit and child-process tests rather than by the live fault. The condemned-scope fixes above are likewise proven against a fake dialect and a mocked `runMigrations`, not against a live reaped backend. Also not verified: the synchronous `execute` → `write(Sync)` path at `connection.js:179` was never observed live, only the `setImmediate` one — the recogniser covers both by frame, and the unit test for it uses a hand-built stack. The driver-side fault is worth an upstream report (`postgres.js` should not perform I/O on the socket whose error it is handling, and `closed()` should null `nextWriteTimer` after clearing it); none is filed here. `#166` — not holding a transaction open across arbitrary user code — remains the structural fix that removes the condition entirely, and is untouched.
