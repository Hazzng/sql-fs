Cap the file size a sandbox `exec` script may read whole or produce with one write, as `MAX_EXEC_FILE_BYTES` (default 8 MiB), rejected as `EFBIG` → 413.

**This removes a capability, deliberately.** A sandbox can no longer `sed`/`tr`/`cat` its way through a file larger than the ceiling, and scripts that did so will now fail. The trade is that they were failing other tenants instead. just-bash's text utilities rebuild strings synchronously on the main thread, and 62.8% of the cost is GC from allocation pressure — so yielding cannot help, only not doing the work can. Measured: `sed s///g` blocks the event loop 706 ms at 8 MiB and 2238 ms at 16 MiB, `tr` 5563 ms at 49 MiB.

Past roughly 2 s the stall stops being a latency problem and becomes a correctness problem for unrelated tenants: `src/redis/client.ts` sets `commandTimeout: 2000`, so a stall beyond it times out in-flight Redis commands belonging to other sandboxes — observed in the harness as `rw_lock_writer_release_error … Command timed out` against a sandbox that had no part in the exec. The `sed` threshold for that is ~14 MiB. 8 MiB is chosen to sit a factor of two under it rather than at it, because the per-byte cost varies by utility (`tr` is worse than `sed`, `wc` is better) and the ceiling has to hold for the worst one.

The ceiling applies **only inside `bash.exec`** — it is scoped by an `AsyncLocalStorage` context, so the HTTP and MCP file routes keep their own, wider caps (`MAX_FILE_WRITE_BYTES`, 50 MiB). A file too large for a script to read is still retrievable whole with `GET /v1/sandboxes/:id/files/*path`, which is the one read path with no size gate at all; MCP `file_read` also serves it, but only below its own 16 MiB ceiling (`MAX_MCP_READ_FILE_BYTES`), so it is an escape hatch with a lid rather than an unconditional one. That asymmetry is the point: moving bytes over HTTP costs one buffer copy, rebuilding them through a shell pipeline costs seconds of GC.

Enforcement is O(1) on the passing path — a store lookup and an integer compare before any blob is fetched, with no extra database round trip and no allocation. An over-cap read is refused without reading the blob at all.

The error message is treated as a deliverable rather than a label, because the caller is an agent that has to recover without a human. It states that the limit is deliberate and the same call will fail again (so retrying is pointless), gives both the attempted size and the limit, names remedies that actually work, and names `MAX_EXEC_FILE_BYTES` for the operator reading the same line in a log. Tests assert the numbers, the env var, the absence of bash's phantom `ENOENT`, **and** the remedy strings — an earlier draft of this message recommended `head -c` / `tail -c` / `split -b` / `sed -n` for reads, and every one of those re-trips the same limit: `IFileSystem` exposes no ranged read and SqlFs implements no `readFileBytes`, so each lands in the same whole-file assert (checked empirically against the installed just-bash with an instrumented `InMemoryFs`). Telling an autonomous agent "do not retry, do this instead" and handing it four commands that fail identically buys a retry loop, so the read remedy now points at `GET .../files/{path}` and says in as many words that slicing in the sandbox does not help. The write remedies do work, with one qualification carried in the message: `split -b` helps only when it reads from a pipe rather than from the oversized file.

**What this does NOT hold: the 2 s wall, per script.** The cap is per file, and that is the whole of it. Verified on the real just-bash: `cat /a.txt /b.txt | wc -c` over two 8 MiB files is two independent in-cap checks and 16 MiB of pipeline work; `sed 's/x/xxxxxxxx/g' 8mib.txt | wc -c` builds roughly 64 MiB of strings from one in-cap input, with the 4x in-memory expansion unchecked and — with no redirect — no write check either. Anything that stalls the loop through a pipeline rather than through one oversized file still gets through. The boundary that would catch it is the pipeline/command-output boundary inside just-bash, which this repo consumes as a dependency and does not modify, so it cannot be fixed here. A cumulative per-exec byte budget was considered and rejected as worse than the gap: it would fail a build touching 100 x 200 KB files, which never stalls anything, while still not bounding a single in-cap file that expands 8x in memory.

This is a stopgap, and now an explicitly partial one. The real fix is moving `bash.exec` off the main thread so the allocations leave the main heap, which removes the ceiling rather than enforcing it (#198); that is tracked separately and is a much larger change, because it has to cross both the `IFileSystem` boundary and the `JUST_BASH_DEFENSE_IN_DEPTH` boundary.
