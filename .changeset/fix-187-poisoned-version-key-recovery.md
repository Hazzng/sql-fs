Repair a structurally invalid Redis version key instead of returning `503 ECOHERENCE` on every write to that sandbox forever.

**One `redis-cli SET` took a sandbox out of service permanently.** `SET vfs:default:ver:<sandbox> not-an-integer` is enough. Redis answers the next `INCR` with `ERR value is not an integer or out of range`, `publishVersionIfDirty` treats that like any other publish failure, and the client gets `503 ECOHERENCE` with `retryable: false`. Correct once: the write did commit, and a blind retry would re-apply a non-idempotent script. Wrong as a steady state, because the failure is permanent. Every later `INCR` fails identically, the #175 deferral never drains, the F3 drainer retries forever, and nothing in the process ever resets the key. Measured on the load harness: writes 2, 3, 4 and 5 on replica A and one on replica B all returned the same 503, six seconds of waiting changed nothing, and the key still read `not-an-integer` at the end.

**A poisoned key and an unreachable Redis now get different answers.** `isPoisonedVersionKeyError` matches exactly two Redis reply prefixes, `WRONGTYPE` and `ERR value is not an integer`, which are the only two ways a key can be structurally un-`INCR`-able. Those get repaired in place with an unconditional `SET` (which replaces a list or hash as happily as a string) and the turn goes on to publish normally, so the write that triggered the repair succeeds instead of 503-ing. Everything else keeps the #186 deferral byte for byte: timeouts, `ECONNRESET`, `READONLY You can't write against a read only replica`, `OOM command not allowed`, offline-queue rejections. The matcher is narrow on purpose. Widening it to "any `ReplyError`" would let a Redis outage silently reset live counters on sandboxes that were never corrupt, so a negative-guard test pins every one of those strings to `false` and fails if the matcher is loosened.

**The reset value is the current epoch in milliseconds, not 1.** The poisoned write destroyed the counter, so its old height is unknowable, and restarting at 1 is not safe: a replica whose `lastSeenVersion` is already 1 would compare equal, never reload, and serve stale reads with no further write to shake it loose. An epoch stamp sits above anything a real counter can reach (it would take about 1.7e12 writes) and grows across repeated resets, so no sibling can be holding it and every warm session reloads on its next freshness probe. Only the difference is load-bearing, so clock skew between replicas does not matter. Verified live: with replica B holding a warm session, a write on A after poisoning healed the key and B then read the new content, and B's own write was visible back on A.

**The F7 destroy tombstone is exempt.** `DESTROYED` is a non-numeric string too, so it fails `INCR` the same way, but it is a deliberate sentinel rather than corruption. Overwriting it with a live counter would resurrect a destroyed sandbox for every replica still holding a warm session. So the repair reads the key first and refuses to touch a tombstone, leaving the caller on the old deferral path. Confirmed on the harness: after a `DELETE` on replica A, an exec against the dead sandbox on replica B still answered `404 ENOENT` and the key still read `DESTROYED`.

**Cost: one `GET` plus one `SET` on a path that previously only failed, and a repair that is a real state change.** Both extra round trips happen only after an `INCR` has already failed with one of the two poison replies, so a healthy sandbox pays nothing. The change worth understanding is that the service now overwrites an operator-visible Redis key on its own. If someone is mid-way through hand-editing a version key, or a future feature parks a non-numeric sentinel there the way F7 does, the next write repairs it out from under them. The `version_key_poisoned_reset` log line carries the tenant, the sandbox, the new value and the Redis reply that triggered it, which is the thing to alert on: a repair means something wrote a non-counter into a counter key, and that cause is still worth finding.

Verified against the two-replica load harness (A on 8101, B on 8102, one shared Redis db 9). Before: five consecutive writes wedged on `503 ECOHERENCE`, key unchanged. After: every write returned 200, the key read an epoch stamp, and the same held for a `WRONGTYPE` key built with `RPUSH`. `concurrency.mjs` stays all-PASS, exit 0. Ten new unit tests, each checked by reverting the source change and confirming the failure (seven fail, the three negative guards pass by design because they assert preserved behaviour). Those three were then checked against mutations of the fix instead: widening the matcher to match everything kills the transport-deferral guard, dropping the tombstone check kills the tombstone guard, and returning the reset version after a failed repair write kills the fallback guard. Three #175 tests changed their stand-in error string from `ERR value is not an integer` to `Command timed out`, because that string now means poison rather than transport and would have made them pass for the wrong reason.

**Not verified.** No test covers two replicas racing a repair on the same key: both would `SET` an epoch stamp within the same millisecond or two, and the last writer wins, which is fine for coherence (both values differ from every sibling's `lastSeenVersion`) but was not exercised. The repair was not run against a Redis that refuses writes, only against one that rejects the command, so the `OOM`-at-`maxmemory` shape reaches the repair's own `SET` only in a unit test. There is also an adjacent read-side problem this does not fix: while a key is poisoned, `ensureFreshCache` clamps the non-numeric value to `0` through `Number(raw) || 0`, so readers converge on `lastSeenVersion = 0` and stop reloading. It is bounded, because the first write on any replica now heals the key and every reader reloads on the next probe, and staleness needs a writer anyway. But the clamp itself is still wrong and is left in place.
