Split the Redis connection by role, cap in-flight blob-cache backfills, scope the circuit breaker per role, and log every breaker transition.

One ioredis connection carried everything: the blob cache, the path snapshot, the version counter and both distributed locks. ioredis pipelines over a single socket, so a queue of multi-MiB blob `SET`s head-of-line blocks the latency-critical commands behind it — measured at 260 in-flight 2 MiB writes, an `INCR` on the shared connection timed out at 2043 ms while the same command on a separate connection answered in 44 ms. Each such timeout drove `breaker.recordFailure()` on the lock acquire path, the process-wide breaker opened at five consecutive failures, and from then on every request on the replica fast-failed with `ELOCKTIMEOUT` → 503 in 1–7 ms without touching Redis at all. Bystander reads died with it, every tenant on the replica died with it, and a 70 s Redis freeze produced 114,213 503s and **zero** log lines beyond request logs, which is why it was originally misdiagnosed as a Postgres problem.

Four changes, all aimed at that chain:

- **Two connections.** `getRedisClient(role)` now returns a separate client per role: `control` (exec and RW locks, version counter, session state) and `data` (blob cache, path snapshot). `REDIS_DATA_URL` defaults to `REDIS_URL`, so existing deployments get the isolation with no config change — the split is by *connection*, not by server. Point it at a second Redis only if you also want physical separation. The server opens the data connection only when a data-plane feature needs it (blob cache, on by default, or path snapshot); a lock-only deployment keeps just the control socket, and path snapshots additionally require the control connection because every snapshot read is version-checked against its counter.
- **Bounded backfill.** `RedisBlobCache.set` is called fire-and-forget from seven sites in the Postgres dialect and had no cap, so a stalled Redis grew an unbounded queue of multi-MiB writes. It now refuses past `REDIS_BLOB_SET_MAX_IN_FLIGHT` (32) concurrent writes or `REDIS_BLOB_SET_MAX_IN_FLIGHT_BYTES` (32 MB) of concurrent payload, and **drops** rather than queues — the cache is fail-open, so a dropped backfill costs one later Postgres read. The budget is held per data CONNECTION, not per cache instance: one `RedisBlobCache` is built per tenant over the single shared data client, so instance-local counters would have let T tenants put T x 32 MB on the one socket the cap exists to protect.
- **Per-role breaker.** `getRedisCircuitBreaker(role)` keys the singleton by role, so the data-plane breaker opening can no longer fast-fail a lock acquire. The blob cache now consults the data breaker and skips Redis entirely while it is open, which also stops a stalled cache adding 2 s of `commandTimeout` to every read. Claiming the half-open probe is a separate, explicit `tryAcquire()`; `isOpen()` is a pure predicate. A caller that takes the probe and then bails out without recording a success or failure never hands it back, and the half-open branch never re-checks the clock — so that shape wedges the breaker open for the process lifetime. The backfill capacity checks therefore run before the breaker is consulted, and `mdel` (which records neither outcome) only reads the pure predicate.
- **Recovery is the probe's job alone.** Two more ways a stalled Redis's own traffic could stall the breaker's recovery, both the same shape as the wedge above. A command admitted while the breaker was still closed reports its outcome after it has opened; that straggler says nothing about the present. Such a late *failure* used to restart the whole `openMs` cool-down, so a burst of them — up to the backfill cap, all expiring on the same 2 s `commandTimeout` — could push the half-open probe out of reach for as long as they kept landing. A late *success* used to close the breaker outright, releasing the whole replica onto a Redis nothing had re-tested. Results arriving while open are now ignored: only a half-open probe closes the breaker, and only a fresh open or a failed probe restarts its clock. Capacity drops deliberately still do **not** count as failures — the backfill queue saturates under ordinary high-throughput writes (measured: 411 drops in a storm run with zero 5xx), so treating them as evidence of a stall would trip the data breaker exactly when Redis is healthy.
- **Transition events.** Opening logs `redis_circuit_open` (with `role`, `threshold`, `openMs`); closing logs `redis_circuit_closed` (with `role`). Only real transitions log — `recordSuccess()` runs on every acquire and must not flood. Dropped backfills log `redis_blob_set_dropped` with the running total, throttled to one line per 5 s.

**Measured on the multi-replica harness** (`redis-storm.mjs pause`, a 6 s `CLIENT PAUSE` against the isolated replica), same machine, immediately before and after: 5xx fell from **90.0%** (6899/7666) to **54.3%** (2289/4217) and **54.2%** on a repeat run, successful operations in the same window rose from 767 to ~1900, and `version_incr_error` — the control plane being starved by cache traffic — fell from 4 to 1. The breaker now announces itself: the control breaker opened once and closed, the data breaker cycled three times, all visible in the log where previously there was nothing.

**The cost, and what this does not fix.** A second connection is a second socket, a second TCP keepalive and a second entry in Redis's `maxclients` per replica — negligible per process, worth knowing at high replica counts. More importantly, 54% is not 0%: a `CLIENT PAUSE` stalls the *server*, so both connections stall together and the control breaker still opens. The split removes the coupling through the client-side command queue, not the coupling through a single Redis server — separating those requires `REDIS_DATA_URL` pointing at a different instance, which is now possible but is a deployment decision, not a default. Requiring `allkeys-lru` on the cache Redis (recommendation 4 in the issue, and the reason the `maxmemory`+`noeviction` variant never recovered) is not in this change.

**What separation actually buys, measured.** Pointing `REDIS_DATA_URL` at a second instance was then tested directly: one replica with the control plane on one Redis and the data plane on another, mixed reads and writes, pausing each plane in turn.

| paused plane | ops | 5xx / timeout | max |
|---|---|---|---|
| data (blob cache, path snapshot) | 12,584 | **0 — every request 200** | 2,014 ms |
| control (exec lock, RW lock, version counter) | 26,643 | 25,248 (**94.8%**) | 4,086 ms |

A data-plane outage is invisible to clients: the blob cache fails open, so a miss falls through to Postgres, and writes never needed it — `commitBlob` goes to Postgres and the Redis `set` is a fire-and-forget backfill. A control-plane outage fails ~95% of requests and *must*: a write that cannot take its lock has no safe outcome but to fail, and since reads take the shared RW lock they block too. So the ~54% measured on the single-instance harness is a property of sharing one Redis, not a ceiling on this change — with `REDIS_DATA_URL` split, the data plane can be down entirely and nobody notices.

Not verified: behaviour against a genuine network partition, or against Azure's managed Redis — the two-instance test above used two local containers. The `maxmem` and `freeze` storm variants were not re-measured after the split.
