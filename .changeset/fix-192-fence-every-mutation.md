"sql-fs-api": patch

Put every filesystem mutation behind the epoch fence, and make every one of them advance `sandboxes.version` — not just the four composite writes.

**Ordinary traffic was quietly disarming the fence.** #161 gates the conditional `version` bump inside the advisory-locked `ctx` CTE of `writeFileComposite`, `mkdirComposite`, `rmComposite` and `mvComposite`. Fourteen other call sites reach Postgres some other way — `bulkIngest`, `mkdir -p` (per segment), `rm -r`, `cp`, `cp -r`, `link`, `symlink`, `chmod`, `utimes`, and the non-composite `writeFile`/`appendFile`/`mkdir`/`rm`/`mv` fallbacks. The obvious consequence is that a zombie writer could still lose an update through one of them, #170's class through a different door. The subtler and worse one is that they did not *advance* the counter either: a perfectly **live** writer using only these left `version` where it was, so the next genuinely stale writer's pin still matched and sailed through. Measured end to end on the harness, `sandboxes.version` after each shell command on a fresh sandbox: before, `echo`, `cp`, `chmod`, `mkdir -p /x/y/z`, `ln`, `touch`, `rm -r` left it at `1, 1, 1, 1, 1, 1, 1`; after, `1, 2, 3, 6, 7, 8, 11`.

**The fence rides inside a statement each path already issues, so it costs no round trip.** Six dialect methods became fence carriers — `createInode`, `updateInode`, `incrementNlink`, `deleteDirent`, `moveDirent` and `bulkIngest`'s preamble — each prefixed with the composites' own `ctx`/`advanced`/`epoch` CTEs via a shared `PostgresDialect.fenceAndAdvance`, and each gating its mutation on the `epoch` CTE so a rejected fence makes the write *unreachable* rather than merely rolled back. Every one of the fourteen call sites runs at least one carrier, so none needed a bump statement of its own: `chmod`/`utimes` are `updateInode`, `link` is `incrementNlink`, `rm -r` is `deleteDirent`, the `mv` fallback is `moveDirent`, everything that creates an inode is `createInode`, and a whole `bulkIngest` batch is one bump folded into the `SELECT id, root_inode` it already ran. `mkdir -p`, `cp -r` and `rm -r` bump once per entry they actually touch, the way `mvComposite` has bumped twice since #161. The carriers deliberately omit the composites' `set_config('app.sandbox_id')` and `pg_advisory_xact_lock`: they are reached only through `SqlFs.#withWriteTx`, which has already issued `setSandboxContextWithLock` on that transaction, and re-evaluating both would buy nothing. The fence GUC refresh stays `set_config(..., is_local = true)` — transaction-scoped, rolled back with the write, pooler-safe.

**`SqlFs` keeps the pin honest, which is where the only added round trips are.** A write that advances `version` without telling the session would fence that session out of its own next scope. Outside a script scope `#withWriteTx` re-reads the epoch inside the same transaction after the write, exactly as `#withBareTx` has done for the composites since #161: one extra round trip per mutating HTTP request, none for exec. Inside a scope nothing is re-read per write — the pin is allowed to lag the transaction-local `app.sandbox_epoch`, which is precisely what #161's `version > expectedEpoch AND version = app.sandbox_epoch` branch exists to admit — and `endScriptScope` settles it once before COMMIT, and only when one of these paths actually ran. A composite-only script pays nothing. Measured: 200 `chmod`s in one exec move `version` 1 → 201 in 89 ms, and a `load.mjs` ramp on this machine is within noise of the same build without the change (1934 vs 1812 ops/s at C=32, 1874 vs 1902 at C=16).

**Behaviour change: `cp`, `chmod`, `ln`, `touch`, `mkdir -p`, `rm -r` and ingest can now fail with `409 ESTALE`.** They never could before, because they never consulted the epoch. It fires under the same condition the composites already use, and `ESTALE` already maps to a retryable 409 — no new error code. The flip side is the fix itself: a peer doing nothing but `chmod` now fences a stale writer where it used to wave it past. Three dialect methods gained a required `sandboxId` parameter (`updateInode`, `incrementNlink`, `deleteDirent`; `moveDirent` and `bulkIngest` likewise) because they had no other way to name the row they fence on; a dialect that ignores `expectedEpoch` simply does not fence, and the parameters are inert to the write itself.

Verified: 20 new unit tests and 7 new integration tests against a real Postgres, plus the per-command table above taken through the HTTP API on the load harness, against a base-branch replica on the same database for contrast. Each source change was reverted in isolation and the failure confirmed — reverting the dialect fails 4 of 7 integration tests (`['cp', false]`, `expected 0n to be 3n`, `'accepted'` where `'ESTALE'` was expected); reverting `sql-fs.ts` fails 16 of 20 unit tests and 3 of 7 integration tests; dropping just the end-of-scope re-pin fails exactly the two tests that claim to cover it, with the integration one surfacing as a real `ESTALE` thrown at a session that did nothing wrong; dropping just the post-write epoch read outside a scope fails the other two. `concurrency.mjs` stays all-PASS exit 0 and `replica-steal.mjs` still reports "the property holds".

**The vacuous-pass trap, recorded because the next fix will meet it too.** A half-fix that still *throws* `ESTALE` but stops gating the mutation on the `epoch` CTE passes six of the seven integration tests: the transaction rolls back either way, so a write that should have been unreachable is invisible. The one test that catches it swallows the `ESTALE` and lets the transaction COMMIT, then asserts the row is untouched — mode still `0o644`, `nlink` still 1, the dirent still there. Without that test the whole suite is theatre.

**Not verified.** No cross-replica reproduction of a zombie arriving through one of these doors on the live harness: `replica-steal.mjs` still exercises only the `appendFile` composite, and the stale-pin integration tests model the lapsed lease as "context without the locking variant" rather than as an expired Redis lease. The per-statement fence is inert in the shape the service actually runs — a transaction that refreshed `app.sandbox_epoch` at open admits any older pin through #161's escape-hatch branch, which was confirmed to behave identically for `mkdirComposite` and for the new carriers, so this change neither widens nor narrows that; the real fence remains the scope-open pin comparison, and this change is what keeps that comparison meaningful. `symlink` is fenced and tested but nothing in the service sets `allowSymlinks`, so it has no live exercise. No other dialect exists to check the optional-fence fallback against, only a fake. Delete/recreate still resets `version` to 0 (#136); the `sandbox_epochs` tombstone is untouched. Two adjacent defects were found and left alone: `advisory-lock.integration.test.ts` (4 tests) and `blob-decoupled-tx.integration.test.ts` (1 test) fail identically on the base branch against this database, and `bulkIngest` still upserts blobs inside the caller's transaction rather than through the decoupled `commitBlob` that F6 introduced for `writeFile`.
