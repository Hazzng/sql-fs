Put every filesystem mutation behind the epoch fence, not just the four composite writes.

**The fence had eight doors left open, and the second problem is worse than the first.** PR #191 added `sandboxes.version` and gated a conditional bump inside the advisory-locked `ctx` CTE of `writeFileComposite`, `mkdirComposite`, `rmComposite` and `mvComposite`. `bulkIngest`, `mkdir -p`, `rm -r`, `cp`, `cp -r`, `link`, `symlink`, `chmod` and `utimes` never touched that path. The obvious consequence is that a zombie writer could still destroy a live writer's commit through one of them — #170's class, reached by a different door. The subtler one is that they did not *advance* the counter either: a perfectly **live** writer using only these operations left `sandboxes.version` where it was, so a genuinely stale peer's pinned epoch still matched and its next composite committed straight over the top. Ordinary traffic silently disarmed the fence for everyone else. Both are now reproduced as actual lost updates in `integration/epoch-fence-multi-statement.integration.test.ts`, not merely as missing throws.

**The list in #192 was close but not right, and it was never checked against the code.** Enumerating the mutating methods on `SqlFs` and following each to the dialect gives: `bulkIngest`, `mkdir -p`, `rm -r`, `cp` (single-file **and** recursive — the issue counted them as one), `link`, `symlink`, `chmod`, `utimes`. `truncate` does not exist — `IFileSystem` has no such method and `SqlFs` implements none; shell truncation (`> file`, `truncate`) lands in `writeFile`, which was already fenced. `mv` is on the issue's unfenced list nowhere and correctly so — it has had `mvComposite` since #191. One thing the issue missed entirely: the **non-composite fallback branches** inside `writeFile`, `appendFile`, `mkdir` and `rm`, taken when a dialect exposes no composite. Postgres always does, so they are unreachable today, but they are the shape a second dialect would arrive in and they are fenced too. `symlink` is reachable only with `allowSymlinks: true`, which nothing in the service sets — it is `EPERM` by default. It is fenced and tested anyway rather than skipped on a default that a future caller can change.

**These cannot become composites, so the fence is a statement of its own — placed first, which is the whole trick.** `mkdir -p` creates a variable number of directories, each needing the previous one's generated id; `rm -r` and `cp -r` walk a snapshot of the in-memory subtree; `bulkIngest` is already a multi-row bulk insert. There is no single CTE to hang a `fence` branch on. `SqlDialect.bumpSandboxVersion` applies exactly the bump the composites embed — same advisory lock, same RLS context, same `version = COALESCE($epoch, version)` guard, ESTALEEPOCH on zero rows — and `SqlFs.#fencedWrite` issues it as the **first** statement of the same transaction. A stale pin therefore throws before a single mutating statement is issued: the writes are *unreachable*, not merely rolled back, so nothing depends on anyone honouring the ROLLBACK. Failure handling matches `#fencedComposite` exactly — the verdict is sticky inside a script scope (`#scopeFenced`), so a bash script that swallows the error still rolls back instead of committing and reporting exit 0, and the in-memory pin is left where it was so a retry without a reload stays fenced.

**Cost: one extra `UPDATE` per mutation, and one row lock held to commit.** For `bulkIngest` that is one statement for the whole batch however many files it carries — ingesting a 500-file tarball costs one added round-trip, not 500. `mkdir -p` is the exception, bumping once per segment it actually creates (`mkdir -p /a/b/c` on an empty tree costs three), because batching its segments into one transaction would change its partial-failure behaviour, which is not this fix's business; a `mkdir -p` over an existing tree creates nothing and costs nothing. Inside a script scope every statement rides the already-open script transaction, so the transaction count is unchanged and only the statement count moves. The `sandboxes` row lock the bump takes is held to commit, but the composites have taken it since #191 and in the same order (advisory lock, then row), so there is no new lock-ordering cycle between sandboxes — a second replica writing the same sandbox was already serialized on the advisory lock before it could reach the row.

**Behaviour change worth knowing: `cp`, `chmod`, `link`, `utimes` and ingest can now fail with `503 ESTALEEPOCH` (retryable).** They never could before, because they never consulted the epoch. This only fires when another replica has genuinely committed to the same sandbox since this session pinned its cache — which is exactly the case where the old behaviour silently destroyed data — and the session's next reload re-pins and lets it through. The flip side is that the counter now moves on operations that previously left it alone, so a peer doing nothing but `chmod` will fence a stale writer where it used to wave it past. That is the fix, not a side effect: the fence's precision is only as good as the counter's completeness.

Verified: 25 unit tests and 7 integration tests against a real Postgres, plus end-to-end through the HTTP API and real bash on the load harness — `cp`, `chmod`, `mkdir -p` (+3 for three segments), `ln`, `touch` and `rm -r` each advance `sandboxes.version` where all of them left it at its previous value before. Each source change was reverted in isolation and the failures confirmed: removing `bumpSandboxVersion` from the dialect fails all 7 integration tests; removing `#fencedWrite` and its call sites fails 23 of 25 unit tests and 5 of 7 integration tests. `concurrency.mjs` stays all-PASS exit 0 and `replica-steal.mjs` still reports "the property holds".

**The vacuous-pass trap this fix walked into, recorded because the next one will too.** Moving the bump from before the writes to after them — a plausible half-fix that fences nothing — leaves **all 7 integration tests passing**. SqlFs throws either way and the transaction rolls back either way, so the damage is real and invisible. Only the unit tests catch it, because they assert the dialect *call order* and that a fenced op reaches the dialect as the bump and nothing else; 18 of them fail on that variant. An integration test cannot see this: there is no way to commit the half-applied transaction from outside SqlFs, which is where the equivalent #131 test got its leverage.

**Not verified.** No cross-replica reproduction of a real zombie through one of these doors on the live harness — the integration tests model the zombie as "A simply never reloaded", which is the same state but arrives there without a lapsed Redis lease; `replica-steal.mjs` still exercises only the `appendFile` door. `symlink` is fenced and unit-tested but has no live exercise, since nothing in the service enables it. No other dialect exists to check the optional-method fallback against, only a mock. The added `UPDATE` was not benchmarked; the cost claims are statement counts, not measured latency. Two adjacent defects were found and left alone: the integration suite deadlocks against itself when several test files run `runMigrations` concurrently against one database (`Migration failed for tenant "default": deadlock detected`, present on the base branch at the same rate), and `bulkIngest` still upserts blobs inside the caller's transaction rather than through the decoupled `commitBlob` that #F6 introduced for `writeFile`, which is the actual source of the cross-sandbox `blobs` deadlocks in that suite. Delete/recreate still resets the epoch to 0 (#136).
