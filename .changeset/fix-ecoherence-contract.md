Split the 503 contract so a client can tell an applied-but-unacknowledged write from one that never landed, stop telling clients to retry a committed write, and stop 503-ing a request that mutated nothing.

**What a client must now do differently.** Every error body from the global handler (and the SSE `error` frame) carries a new boolean `retryable`. `true` means the server knows the operation that failed applied nothing and the condition is transient — an automatic retry is safe. `false` means the effect may already be durable, or a retry would fail identically. Branch on that field instead of on the status code: several distinct codes share 503 and they disagree about durability. `ELOCKTIMEOUT`, `ELOCKLOST`, `ESESSIONCLOSING`, `ESHUTTINGDOWN`, `ERUNTIME_BUSY` and the Postgres capacity refusals (`53300`/`53400`/`57P03`) are `true`. `ECOHERENCE` and the new `ELOCKLOST_APPLIED` are `false`. The `08xxx` connection-exception class is also `false` — a connection lost mid-`COMMIT` leaves the outcome in doubt, which is not the same as known-not-applied, and this is the one place where being vague would cost a double-apply.

**The guarantee is per operation, not per request.** A route that runs several independent transactions can have committed an earlier one before a later one fails retryably. `POST /v1/sandboxes` persists the sandbox row, then builds the FS, then writes initial files, each in its own transaction, and `withSession` opens no script transaction at all — so a `53300` on a later step answers `retryable: true` with the sandbox row already durable, and a blind retry orphans a sandbox that still shows in `GET /v1/sandboxes`. The same holds for ingest, and for an `ESESSIONCLOSING` raised between steps. The field's documentation now says this explicitly: for the non-idempotent multi-step routes, retry then reconcile. Single-transaction routes (exec, the file routes) are fully covered. Making those routes atomic, or carrying a per-request commit flag on the Hono context, is the real fix and is deliberately not in this change.

**A lease lost after the commit is no longer advertised retryable.** `withDistributedLock` wraps `getOrCreate` + `withSessionEntry`, so a successful `fn` return means the script transaction already COMMITted and the version INCR already ran. The lock layer then re-checked the `lost` flag and threw `ELOCKLOST` — which this very change advertises as `retryable: true`. The F2-L1 pre-commit guard closes the common case (it keys off `lockLostSignal` before `endScope`), but `markLost()` fires from a heartbeat tick and can land during the COMMIT itself or the Redis INCR after it; the window is small and the cost is a double-applied `echo L >> /counter.txt`. A loss observed *after* `fn` returned is now `ELOCKLOST_APPLIED` (503, `retryable: false`) and logs `lock_lost_post_commit` at `critical`. Read paths — the RW lock's shared mode, and the legacy single-key lock taken with `readOnly: true` — keep the retryable `ELOCKLOST`, because a reader runs under a read-only scope and commits nothing.

**No existing client behaviour silently becomes wrong.** Both first-party SDKs already refuse to retry a write exec on `503 ECOHERENCE` by inspecting `code`, so the dangerous path was already closed for them; they simply do not consume the new field yet. A hand-rolled client that retried *all* 5xx was already double-applying writes before this change — it now has a field to fix that with. The field is additive, so a client that ignores it behaves exactly as before.

**The message was the thing telling clients to do the unsafe thing.** `session-manager.ts` said *"ECOHERENCE: write committed but version publish failed; **client should retry**"* while `openapi-spec.ts` said *"Never causes retry on 503 ECOHERENCE for write execs"*. The spec was right and the message was both wrong and self-contradictory — it announced the write had committed and then told you to re-run it. Confirmed on the two-replica harness by poisoning the version key (`SET vfs:default:ver:<sandbox> not-an-integer`) so only the `INCR` fails: one healthy exec plus three `503 ECOHERENCE` execs of `echo L >> /counter.txt` left **four** lines in the file. Every 503 had committed. The message now reads "the write IS applied — do not blindly retry".

**The poisoned half of the code is now its own code.** `publishVersionIfDirty` threw `ECOHERENCE` for two opposite situations: the `INCR` failed after a successful `COMMIT` (applied), and the cache was poisoned by a failed `COMMIT` plus a failed recovery reload (Postgres rolled it back — nothing applied). The second is now `ECOHERENCE_UNAPPLIED`, 503, `retryable: true`. It is not reachable from an HTTP response today — poison is only ever set on a path that also throws its own error, which wins — so this is a contract correction rather than an observable behaviour change, but it means the code can never mislabel a rolled-back turn as applied if that path becomes reachable.

**A request that mutated nothing no longer inherits a previous turn's failure.** Once `publishPending` was set, every later turn on that session re-attempted the stranded `INCR` and, on failure, threw — so an exec that only read files answered `503 "write committed but version publish failed"`, which is false for that request. The `INCR` is still attempted (the healing is not skipped); its failure is now deferred to the background publish drainer, which already owned the retry. On the harness, a `cat /counter.txt` exec against a poisoned key went from 503 to 200 while the mutating execs kept their (correct) 503. Reads through `GET /files` and `GET /tree` were already unaffected — they take the shared lock, which does not publish.

Cost: one extra boolean per error body, and two new documented error codes (`ECOHERENCE_UNAPPLIED`, `ELOCKLOST_APPLIED`). No new Redis or Postgres work — the deferral strictly removes a throw. `openapi-spec.ts` gains the `retryable` schema field, a documented `503` response on all three exec routes, and corrected `retryOn5xx` wording.

Verified by unit tests; each was checked by reverting its source change in isolation and confirming the failure. Not verified: the persistently-poisoned key still wedges writes on that sandbox indefinitely with `ECOHERENCE` — recovering from a non-transient `INCR` error (`ERR value is not an integer`, `WRONGTYPE`) by resetting the key or tearing the session down is the remaining recommendation in the issue and is deliberately not in this change. Neither SDK was updated to consume `retryable`, and neither knows `ELOCKLOST_APPLIED` — a client that special-cases `ELOCKLOST` to retry will now see an unknown code instead, which both SDKs treat as non-retryable, so the change is safe in the conservative direction. The post-commit lock-loss window is proven with a Redis fake whose renew always reports loss, not against a real lease expiring mid-COMMIT. The `ECOHERENCE_UNAPPLIED` path is asserted against `SessionManager` with a stub FS, not against a real correlated Postgres outage.
