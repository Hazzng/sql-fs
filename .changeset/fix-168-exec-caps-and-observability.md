Stop the bulk-write route being a wider door than the single write it batches, cap its request body, and give the event-loop lag monitor an egress and a signal that a real stall actually moves.

**Breaking for anyone sending bulk writes above 50 MiB.** `MAX_BULK_WRITE_BYTES` defaulted to **128 MiB** against a `MAX_FILE_WRITE_BYTES` of 50 MiB — the bulk route accepted 2.5x what the single-file route did, and a 120 MiB batch blocked the event loop for **669 ms**, which on one process and one loop is 669 ms of every other tenant's latency. It now defaults to `MAX_FILE_WRITE_BYTES` and is derived from it, so the two cannot drift: a batch costs no more synchronous work than the widest single write the service already accepts. A caller currently sending a total between 50 MiB and 128 MiB now gets `413 PAYLOAD_TOO_LARGE` where it previously got `204` — set `MAX_BULK_WRITE_BYTES` explicitly to keep the old ceiling, understanding what it buys. The per-entry cap was already closed on `/writeFiles`; this is the total.

**The create route was a second door onto the same work.** `POST /v1/sandboxes` accepts an optional `files` map and writes it exactly the way `/writeFiles` does, but it re-derived its own limits from the same two env vars with different defaults — so with the knobs unset it still accepted **128 MiB** after `/writeFiles` came down to 50 MiB — read them with a bare `Number()` rather than `positiveIntEnv`, so `MAX_BULK_WRITE_BYTES=fifty` made the cap `NaN` and removed it entirely, and applied no per-entry cap at all. All three limits now come from `lib/env.ts`, which is what makes "largest single file body any write surface accepts" true of `MAX_FILE_WRITE_BYTES`. A create carrying between 50 MiB and 128 MiB of initial files now gets `413 PAYLOAD_TOO_LARGE`.

**`POST /writeFiles` had no body cap at all.** Every other write route counts the body off the stream through `writeBodyLimit`; this one did not, so an over-declared or chunked body was JSON-parsed into memory before anything looked at its size, bounded only by the 256 MiB global backstop. It now carries the same middleware — a declared length over the cap is refused unread, and every byte is counted as it streams, so a chunked body carrying no header (or one that under-declares) is cut off rather than trusted. The wire cap is **twice** `MAX_BULK_WRITE_BYTES`, not equal to it: the content caps are on decoded bytes while JSON string escaping roughly doubles the wire size of newline- or quote-heavy text, so an equal cap would reject legal batches. It is a backstop on the parse, not a second content cap.

**The lag histogram had no consumer.** `eventLoopLagSnapshot()` had zero non-test callers — not a route, not `/readyz`, not a metrics endpoint — and the only egress was a `console.log`, so nothing could poll how close a replica was running to the 2 s Redis `commandTimeout`. `GET /readyz` now carries it as an `eventLoop` object. The field is **absent**, not null or zeroed, when the monitor was never started (any embed that does not boot through the entry point), so an idle loop and an unmeasured one cannot be confused. Reading does not reset the histogram, so scraping never erases a window the sampler is about to log. Folded in because exposing it made the type lie visible: an empty histogram reports `mean` as `NaN`, which `JSON.stringify` renders as `null` where the type promises a number.

**A lone stall now moves something other than `maxMs`.** A 2.2 s stall inside a 10 s window is a couple of tenths of a percent of ~400–500 readings, so it lands above `p99` by construction and `p50Ms`/`p99Ms` sit at the histogram floor regardless. Two additions: `p999Ms`, the percentile that does answer for a single outlier at that sample count, and an `event_loop_stall` line at `severity:"critical"` emitted whenever a window's `maxMs` crosses `EVENT_LOOP_STALL_THRESHOLD_MS` — defaulting to **2000**, which is not a round number but the Redis client's `commandTimeout`: past it a stall stops being a latency problem and starts timing out in-flight commands belonging to *other* tenants' sandboxes. It reuses the `heartbeat_gap` severity shape rather than introducing a metrics system.

**Cost, and why the sampling interval did not change.** `DEFAULT_RESOLUTION_MS` stays at 20 ms deliberately: the resolution is not what hid the stalls. Lowering it makes the dilution strictly worse — more readings per window, a smaller share each — while doubling the libuv wakeups; raising it to 100 ms would let a lone stall reach p99 only by discarding every reading below 100 ms. The idle cost is unchanged either way: 50 libuv timer wakeups per second, each a clock read plus one HDR-histogram record, order 1e-5 of a core. `p999Ms` is one extra `percentile()` call per window (once per 10 s) and one extra JSON field; the stall line costs one comparison per window and is silent below the threshold. `/readyz` gains five histogram reads per probe.

**Not addressed, and deliberately so.** This is the set of concrete defects #168 documents alongside its headline; the headline itself — sandbox `exec` having no file-size ceiling, so `sed` over 16 MiB blocks the loop for ~2.2 s with 62.8% of the CPU in GC — is untouched. Neither of its two real cures (a size ceiling inside `SqlFs`, or moving `bash.exec` to a worker thread) is here, and #168 stays open for them. The `heartbeat_gap` threshold is still `REDIS_EXEC_LOCK_RENEW_MS` (20 s), so it still cannot fire below a 20 s stall.

Verified by 12 unit tests, each checked by reverting its source change in isolation and confirming the failure; `p999Ms`, the stall line, the `NaN` guard, the `/readyz` field, the bulk total and the body cap were each reverted separately. The load harness's `concurrency.mjs` stays all-PASS. Not verified: no measurement of the 128 MiB → 50 MiB change against a real 120 MiB batch (the 669 ms figure is quoted from the issue, not re-measured); the idle-CPU figure for the monitor is an order-of-magnitude estimate from the work per sample, not a profiler measurement; `p999Ms` was not exercised against a real 10 s production window, only against the equivalent sample counts. Note that `p99.9` resolves a *single* outlier only while a window holds fewer than ~500 readings — at the default 20 ms resolution a 10 s window holds ~400–500, so it works there, but `maxMs` and `event_loop_stall` are the signals that always do.
