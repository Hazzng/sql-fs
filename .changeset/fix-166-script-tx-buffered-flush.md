"sql-fs-api": patch
---

Stop holding a Postgres transaction open across a user's bash script. Buffer the script's metadata mutations and flush them in one short transaction at scope end.

**A script scope pinned a pooled server connection for as long as the script ran.** `SqlFs.#openScriptTx` opened a transaction on the first mutation and parked inside it awaiting an end-promise that nothing resolved until `endScriptScope`, so one backend sat `idle in transaction` through every `sleep`, Python step, network fetch and `git clone` in between — and, since F6, each write also needed a *second* pool connection for `commitBlob`. Under transaction-mode pooling, which is how production connects and the only thing Azure's built-in PgBouncer offers, that wedges the pool at roughly `default_pool_size` concurrent writers: the harness measured 12 concurrent 8-second writes against `pool_size 12` as a permanent deadlock with a 69 s transaction age, health endpoints included. This is not a regression — `thoughts/shared/plans/2026-05-02_bulk-fs-ops-script-tx.md` recorded in advance that script-tx requires a *session* pooler. It is a design whose stated prerequisite the deployment no longer provides.

**Mutations now go into an in-memory journal and one short advisory-locked transaction replays it at `endScriptScope`.** Every metadata write funnels through a single new gate, `SqlFs.#mutate`, which either runs the dialect call now (outside a scope, byte-identical to before) or records the same closure for replay. The flush issues the same statements in the same order, so the composites' fence-and-advance CTEs, the `nlink` delete/decrement split and the `ON CONFLICT` upserts are all unchanged — `sandboxes.version` still moves by exactly the amounts #161/#204 established (`fresh 0 → echo 1 → cp 2 → chmod 3 → mkdir -p /x/y/z 6 → ln 7 → touch 8 → rm -r 11`, verified through the HTTP API on the harness and pinned as an integration test against both shapes). **File bytes are never buffered**: `commitBlob` still commits content eagerly on its own self-committing connection before the metadata is recorded, and the 3 h GC grace window (`BLOB_GC_MIN_AGE_MS`) already covers a blob that is written but not yet referenced, so the journal holds ~200 bytes per operation. `writeFileComposite`'s `data` parameter became optional for this: it exists only for the dialect's Redis backfill, which `commitBlob` has already done, and passing an empty array instead would have cached a zero-length blob under a real sha.

**The headline number, which is the point of the change.** `max(now() - xact_start) WHERE state = 'idle in transaction'`, sampled from a separate connection while `echo a > /f1; sleep 3; echo b > /f2` runs: **2.98 s before, 0 s after** — at 10 ms sampling resolution the flush never even reaches `idle in transaction`, because it is executing the whole time. The flush itself logs `event:"script_tx_flush"` at 5–16 ms for ordinary scripts. Against a **real Neon transaction pooler** with 40 concurrent 8-second write execs: peak idle-in-transaction age **8.60 s across 40 backends before, 0.50 s across 18 after**, 40/40 succeeding either way (that Neon compute's `max_connections` is 901, so the pool ceiling itself was out of reach there). The ceiling is covered instead by an integration test that sets `PG_POOL_MAX=1`, where the two-connections-per-write requirement becomes fatal rather than merely expensive: the buffered script finishes in 15 ms, the legacy one wedges until the test's 5 s deadline.

**Three behaviour changes, all of them real.**

*Error timing.* Constraint errors the dialect raises — `moveDirent`'s `ENOENT`, `rmComposite`'s `ENOENT`, a unique violation translated to `EEXIST` — move from the failing command to the flush. Bash sees the command succeed and the *request* fails afterwards. This only fires when the pathCache and the database have diverged, which is supposed to be impossible; adding per-mutation DB validation to preserve the old timing would give back most of what the change buys.

*Cross-replica overlap.* The script-long `pg_advisory_xact_lock` is gone with the script-long transaction, so two replicas writing one sandbox are no longer serialized at the database for the script's duration. The epoch fence is what replaces it and it is stricter, not weaker: the flush pins `sandboxes.version` under the writer lock and compares it to the epoch this session's caches were built on, so an overlap that used to *queue* now fails the loser with `ESTALE` → 409 and rolls its whole script back. `replica-steal.mjs` shows exactly that — `A http/exit: 409` where it used to be a silent `200` over a lost update — and still reports "the property holds".

*A new error code, `ENOBUFS` → **413**.* At the buffer cap the script fails and **nothing is applied**: the buffer is discarded without a transaction ever opening, and the scope is condemned so a later command in the same script cannot flush the truncated prefix. Auto-flushing would silently split one commit into two and break the per-script all-or-nothing guarantee that `ELOCKLOST`'s documented "not committed" claim and #170's verified rollback behaviour both rest on. It is known-not-applied but deliberately absent from `RETRY_SAFE_ERROR_CODES`, because that set also promises the condition is transient and an identical re-run hits the identical cap; the message says to split the work instead. Defaults are `SCRIPT_TX_BUFFER_MAX_OPS=50000` and `SCRIPT_TX_BUFFER_MAX_BYTES=33554432`, chosen to be unreachable: just-bash caps a script at 10,000 commands, and the heaviest script the harness could run — 3,317 files created across 60 directories, then `cp -r`, a `chmod` sweep and `rm -rf` — buffered 3,317 ops / 648 KiB, with `cp -r` and `rm -rf` of that whole tree costing 1 and 2 ops.

**Rollout.** `SCRIPT_TX_BUFFERED`, **default `true`**. Both shapes stay fully wired and the legacy one is one env var away without a redeploy of code — verified end to end on the harness, where `SCRIPT_TX_BUFFERED=false` emits zero `script_tx_flush` lines and puts the 2.94 s pin back. It defaults on because the defect wedges a whole replica rather than slowing it, so shipping it off would be shipping a fix nobody runs. `SqlFs` itself defaults the option *off*, so a bare `new SqlFs(...)` in a test keeps the old shape; the deployment default lives in `createPostgresSandboxFs` beside the other env reads.

**Provisional inode ids, and why not preallocation.** A buffered `mkdir /a` has to hand the script an id before `writeFile /a/f` can name its parent. Ids are negative placeholders, minted monotonically for the life of the session, rewritten to the real ids after COMMIT; `#realId` resolves one inside a replay closure, which is why the `rm -r` and `cp -r` loops were hoisted out of their transaction callbacks (a deferred closure reading `#pathCache` would walk a subtree its own call had already emptied). The alternative — preallocating from `inodes_id_seq` — was rejected: it would need an explicit-id parameter threaded through six hand-written SQL methods, it leaves sequence gaps on every rollback, and it couples every sandbox in a tenant database to one sequence. Placeholders cost an O(pathCache) remap per flush and change no SQL at all. They cannot escape: `FsStat` has no `ino` field, and the only consumer of `inodeId` outside `SqlFs` is the Redis path snapshot, published after the remap. A placeholder that survives a flush means the replay produced no row for a path the cache claims exists, and that fails the request with `ECOHERENCE` rather than being published.

**`bulkIngest` is deliberately not buffered** and throws `ENOTSUP` inside a buffered scope. It is unreachable there today — both call sites, `POST /v1/sandboxes/:id/ingest/files` and the MCP `ingest_files` tool, go straight at the session and never through `runInScriptTx` — it is already one short transaction, and buffering it would mean predicting the dialect's DB-derived ancestor resolution in JS and holding every ingested byte in the journal. Failing loudly beats silently splitting a script into two commits.

**Cache invariant, restated.** Outside a script scope, unchanged: writes go to the database first, then update the caches. Inside one, the caches may *lead* the database, and only until the scope ends. The lead is closed on every exit — a failed flush reloads committed state and clears the dirty flag, and if that reload also fails the cache is marked poisoned so no version or snapshot is published — and `reload()` stays refused while a scope is open (F4). `DefenseInDepthBox.runTrustedAsync` wraps the flush like every other chokepoint, via `#db`, which also races it against a #169 driver fault.

Verified: 28 new unit tests, 9 new integration tests against a real Postgres, gate at 1465 passed / 4 skipped (baseline 1437) and integration at 146 passed / 0 skipped (baseline 137). Reverting the fix — `#bufferingWrites()` forced to `false` with the bypass tripwire removed — fails 23 of the 28 unit tests and 3 of the 9 integration tests, each on its own assertion rather than a shared guard; the five unit survivors and three integration survivors are deliberate controls that assert the *legacy* shape or the semantics both shapes share. `concurrency.mjs` stays all-PASS exit 0 and `replica-steal.mjs` still prints "the property holds". `load.mjs` across five runs is within this machine's ±25% run-to-run noise (buffered 1714/1551/1958 ops/s at C=16 against legacy 1603/1408), with buffered equal or better at every level from C=4 up and 8–10% lower at C=1–2, where a run is dominated by per-request latency rather than pool contention.

**The vacuous-pass trap here, recorded for the next reader.** A test that checks the resulting filesystem passes identically whether the mutations were applied eagerly on a script-long transaction or buffered and replayed — the tree is the same either way. The tests that actually bite assert *when* the transaction opens (the fake dialect records an open/close window per transaction), that it is not open while the script sleeps, that the writer lock has not been taken mid-script, that the composite was replayed without the file's bytes, and that a path is sitting on a negative id *before* the flush rewrites it. The first cut of four of them passed under the revert until that last assertion was added.

**Not verified.** No run against Azure's built-in PgBouncer — the pooler confirmation is Neon's, and neither reached its own `default_pool_size` ceiling, so the wedge itself is only reproduced at `PG_POOL_MAX=1` in-process. The `#openScriptTx` tripwire that catches a mutation bypassing the buffer is unreachable by construction today and therefore has no test of its own; it exists for the next person who adds a write path. `bulkIngest`'s `ENOTSUP` branch is likewise unreachable in the running service and is covered only against a fake. Memory was reasoned about rather than profiled: the journal's closures were moved into their own scope (`#putFileOp`) so a sibling closure cannot force a file's bytes into the same context object, but no heap snapshot was taken to confirm it. The `ENOBUFS` cap has never been reached by real work — that is the intent, but it means only synthetic tests exercise it. Two pre-existing items were left alone: the `SCRIPT_TX_BUFFERED=false` path still has the two-connections-per-write requirement it always had, and `bulkIngest` still upserts blobs inside the caller's transaction rather than through `commitBlob`.

Path resolution reads the staged cache inside a scope. `realpath` and the symlink branch of the read path resolved through `dialect.resolvePath` and then matched the returned id against the pathCache — wrong twice over while buffering, since the database has not seen the journaled mutations and pathCache ids are provisional placeholders that can never equal a database id. Both now walk the pathCache, which is authoritative for the scope, with the same 40-hop ELOOP guard the dialect applies. Outside a scope the dialect remains the resolver.
