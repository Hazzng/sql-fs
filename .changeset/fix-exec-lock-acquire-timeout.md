Lower the default exec-lock acquire timeout from 300 s to 75 s, and refuse to boot when it is configured below the lease it waits on.

`REDIS_EXEC_LOCK_ACQUIRE_TIMEOUT_MS` defaulted to 300 000 ms with nothing relating it to `REDIS_EXEC_LOCK_LEASE_MS` (60 000 ms) — validation only asserted `>= 0`. A request blocked behind an orphaned lock therefore held its socket and polled Redis on a jittered 25–50 ms sleep (~27 EVAL/s per waiter, ~8 000 round trips over a full window, multiplied by convoy depth) for five minutes before giving up. Worse, 300 s sits above typical ingress timeouts, so the connection was usually severed and the 503 the server eventually produced never reached the client at all. The new default is lease + ~15 s reap margin: long enough that a crashed holder's lease still expires inside the window (automatic recovery, which is the whole point of the lease), short enough that the reply gets back through ingress.

**The cost is real and worth naming.** The longest legitimate holder is a full-length exec, `MAX_TIMEOUT_MS` = 300 s. A caller that arrives behind one now gets `ELOCKTIMEOUT` → 503 after 75 s where it previously had a chance — a slim one, since the old window expired at exactly the moment such an exec finished — of being served by the same request. That is a deliberate trade: the 503 is documented as retryable, and a client retrying twice costs far less than a five-minute convoy of sockets pinned on a lock they may never get. A deployment that genuinely runs long execs back-to-back and wants the old behaviour can set the env var explicitly.

The boot-time assert is the second half. `REDIS_EXEC_LOCK_ACQUIRE_TIMEOUT_MS` must now be strictly greater than both `REDIS_EXEC_LOCK_LEASE_MS` and `REDIS_RWLOCK_READER_LEASE_MS`: a crashed holder's key (or a crashed reader's ZSET entry) is only reaped when its lease expires, so a shorter acquire window converts every crashed-holder wait into a 503 instead of the recovery the lease exists to provide — a failure mode that looks like flaky contention and is invisible in the config. It is checked where the env vars are parsed (`loadExecLockOptions`, moved out of `server.ts`), which means **a deployment that raises the lease past the acquire timeout now fails to start** rather than degrading silently. That is a genuine operational cost: a bad Redis-lock config becomes a crash-looping replica, not a slow one. It is the same bargain the existing `renewMs < leaseMs` assert already makes, and the error names both variables and their values. The library-level `DistributedLockOptions` / `DistributedRWLockOptions` defaults were lowered to match; their asserts are untouched, so callers that deliberately pass a short acquire timeout (the timeout-path tests) keep working.

Not included: threading an `AbortSignal` into `acquireShared`/`acquireExclusive` so an abandoned request stops polling. That is a larger change and lands separately, on top of the `/exec-sync` disconnect fix that removes the main source of long-lived orphan holders.
